# BOOM 基准时间与分钟级上传重构方案

本文档描述对当前「持久历史补录」（原第 8 节）的重构方案。补数据的**读取方式**（从后往前、两分钟步长、`0x3A`/`0x3B`）不变，改变的是**缺口从哪来**、**什么时候上传**，以及**连接不再有时长上限**。

## 1. 为什么要改

老流程的缺口来自「有界调和」：先写粗意图任务（`recent` / `incremental` / `archive`），再用 `HistoryCoverageService.inspect()` 比对本地覆盖，把没有 `ppi_data` 的秒收敛成 `repairRanges`。它有两个固有代价：

- 缺口判定要遍历 `ppi_data.timestamp`，30 天的 `archive` 一次比对要读 86 万个时间戳，所以必须切成 6 小时的 `scan` 窗口分轮推进，引入了 `scan` / `verify` 两类「不代表确认缺数据」的中间态任务。
- 缺口只能靠「本地没有」推断。设备长期关机、没佩戴的时间段与真正丢包的时间段在本地看起来完全一样，只能靠读一遍设备来区分，因此调和窗口推进和真实缺口混在一条队列里。

新流程引入一个**基准时间 `baseline_sec`**，把「已经记账过的时间」和「待补的时间」彻底分开，不再需要对整条时间轴做覆盖比对。

## 2. 基准时间的定义

`baseline_sec`（下称 `B`）满足：

> **`[0, B)` 的每一秒都已经记账完毕**，不需要再补。

「记账完毕」的两种形式：

1. **合格（qualified）**：该分钟的数据完整度达标（第 3 节）。
2. **已确认（confirmed）**：设备已被读取过该时间段，并返回了完整声明范围的响应，确认没有更多数据（未佩戴 / 关机 / 该段设备确实没记）。

**`B` 停驻是预期行为。** 一分钟不合格时 `B` 卡在该分钟起点不动，直到该分钟被补上或被设备确认无数据，才继续前进。`B` 只前进，不后退。

**`B` 之后的时间分两类，都不需要额外的表**：已记账的落在 `vital_ready_ranges` 里，没记账的就是**缺口**——缺口由 `B` 和 `vital_ready_ranges` 直接相减得出，不存表。

一条新增的总原则：

> **尽量减少连接，靠广播读数据。连接一旦发生，它留下的缺秒必须在同一轮消化掉，不能转交给下一次连接。**

连接期间广播是停的，每一次连接都在制造缺秒，所以只有广播给不出的数据（设备 flash 历史、事件、校时）才值得连接。而「连接留下的缺秒」又必须就地消化——否则它会变成缺口、触发下一次连接，形成「连接 → 缺秒 → 连接」的自我咬合。

广播是每秒一帧的实时快照（`utc` + 当前秒的指标），**不携带历史秒**。连接期空洞的消化有两条路：小空洞在广播恢复的第一帧就地推定推进（9.4 的接续判定，成本为零），大到会丢真数据的空洞在断开前读一次设备（9.3）。第 9 节描述这套机制。

## 3. 分钟合格判定

一分钟 `M = [M, M+60)`，判定依据只有一条：`ppi_data` 里该分钟的秒是否存在（`hr`/`spo2`/`ppi` 是否为 0 不影响，只看到不到行）。两个条件同时满足才算合格：

| 条件 | 判据 | 常量 |
| --- | --- | --- |
| 缺失比例小于 1/3 | `missing * 3 < 60`（即 missing ≤ 19） | `MINUTE_MAX_MISSING_RATIO = 1/3` |
| 没有连续缺 9 秒 | 最长连续缺失段 `< 9` | `MINUTE_MAX_MISSING_RUN_SEC = 9` |

第 `s` 秒可以判定，当且仅当 `s + MINUTE_SETTLE_SEC <= now`（5.3 的 `stableCeiling`）。两个条件都要单独检查。

**这两个阈值是「要不要去设备读这一分钟」的触发器，不是最终裁决。** 分钟不合格 → 成为缺口 → 连设备读一次。设备的回答才是终局：

- 设备有这段数据 → 秒数据落进 `ppi_data`，该分钟合格，并入 `vital_ready_ranges`。
- 设备没有这段数据（该段全 `FF`）→ 该段**确认无数据**，同样并入 `vital_ready_ranges`。

所以**任何一次读取都会让缺口消解**，`B` 一定能继续前进。如果只有「取到数据」才算消解，设备确实没记录的那一分钟会永远不合格、`B` 永远卡死——这是必须避免的死循环。

## 4. 两张表

数据库整体重做，不兼容老库（老库遇到问题直接卸载重装）。删掉 `vital_history_tasks` / `vital_history_state`，换成：

```sql
-- 基准时间。只有一行。
CREATE TABLE IF NOT EXISTS vital_sync_state (
  id INTEGER PRIMARY KEY CHECK(id=1),
  baseline_sec INTEGER NOT NULL
);

-- 已记账的连续区间（左闭右开，秒级，不整分钟对齐）。含两类：
--   合格区间（本地数据完整度达标）
--   确认区间（设备已响应并确认该段没有更多数据）
CREATE TABLE IF NOT EXISTS vital_ready_ranges (
  from_sec INTEGER NOT NULL,
  to_sec INTEGER NOT NULL,
  PRIMARY KEY(from_sec, to_sec)
);
```

**区间是秒级的，`B` 也是秒级的，都不整分钟对齐**（理由见 5.1）——对齐会让 `B` 停驻时出现死区。

**没有第三张表。** 缺口不存——它恒等于 `[B, ready[0].fromSec)`（见 5.2）；设备确认无数据也不单独存——它并进 `vital_ready_ranges`。

也不再需要「已分类游标」：分类是幂等的纯本地计算（第 5 节），每次从 `B` 走一遍即可，走多快只取决于 `ppi_data` 的行数。

## 5. 基准时间如何前进

### 5.1 分类 `classifyFromBaseline(nowSec)`

把 `[B, 分类右端)` 从「未分类」变成「已记账」或「缺口」。**分类右端 = 5.3 的 `stableCeiling(now)` = `now - MINUTE_SETTLE_SEC`**，即「最后一秒已等够余量」的时刻。

**分类右端不是整分钟边界。** 第 `s` 秒可以记账，当且仅当它的数据已经稳定，即 `s + MINUTE_SETTLE_SEC <= now`，也就是 `s <= now - MINUTE_SETTLE_SEC`。这个条件对每一秒单独成立，与分钟边界无关，所以右端就是 `now - MINUTE_SETTLE_SEC`，不需要也不应该向上取整到分钟。取整有两个害处：

1. **产生死区，`B` 推不动。** `now = 12:00:38`、`MINUTE_SETTLE_SEC = 10` 时，整分钟版本给出 `12:00:00`。若此刻 `B = 12:00:20`（连接刚结束回到广播），分类右端落在 `B` 之前 → **这一轮等于没判，`B` 一步推不动**。而 `[12:00:20, 12:00:28)` 是广播已恢复、数据已在本地、且已经等够余量的秒，本该正常判定。缺口因此原样留着，下一次检查又拉起一条连接——这正是第 9 节要消除的「反复连接」。
2. **白等最多 60 秒。** `now = 12:01:09` 时整分钟版本给出 `12:00:00`，即整个 `[12:00:00, 12:01:00)` 都已等够 9 秒以上却仍不能判，`B` 干等近一分钟。这是纯粹的延迟，没有任何稳定性上的收益。

**逐分钟判定与秒级右端不冲突。** 判定仍然是按分钟做的（第 3 节的两个阈值是针对一分钟定义的），只是每一分钟的右端不再被整分钟截断：

```
对每个未记账的分钟 M = [M, M+60)：
  可判秒范围 = [M, min(M + 60, stableCeiling(now)))
  在这些秒里求缺失数与最长连续缺失段
  数据尚未到齐的那部分（stableCeiling 之后的秒）留到下一轮再判，不影响本轮已经稳定的部分
```

所以 `now = 12:00:38`、`stableCeiling = 12:00:28` 时，`[12:00, 12:01)` 这一分钟可以判 `[12:00:20, 12:00:28)` 这 8 秒；若这 8 秒都到了，它就对「最长连续缺失」的判定有实际贡献，不再被整分钟下界一笔勾销。

**`B` 因此可以停在任意秒上，不再只是整分钟。** `B` 的语义是「`[0, B)` 已记账完毕」，没有任何理由必须对齐分钟。

**分类产出的是秒级右端，写入 `vital_ready_ranges` 时也不做整分钟对齐。读取侧的 `startSec` 同样不需要对齐**——设备的 `0x3A` 收的就是裸的 UTC 秒，任意时间戳都行（8.1）。整分钟对齐唯一保留的地方是 30 天保留窗口的起点（5.5）。

步骤：

1. 先减去已有 `vital_ready_ranges`，得到本次真正要判定的**未记账分钟**集合。已记账的分钟直接跳过，不需要重判——分类因此是幂等的。
2. 一次查询取出这些分钟范围内 `ppi_data` 的 timestamp。
3. 走区间算术求出缺失秒与**最长连续缺失段**，逐分钟判定：
   - 合格 → 合并进 `vital_ready_ranges`（与上一条相邻就延长它）。
   - 不合格 → 不记任何东西。它自动成为缺口，由 5.2 与读取路径消费。

**没有单轮扫描上限。** 老流程的 6 小时 `HISTORY_RECONCILE_SCAN_SEC` 是为了限制「遍历 30 天 86 万个时间戳」，而现在：查询只覆盖未记账分钟，App 关闭期间 `ppi_data` 为空（查询瞬间返回零行），区间算术在内存里做。所以 3 天的空白是一次零行查询 + 4320 次分钟算术，没有理由截断。

### 5.2 缺口 `listRepairGaps(nowSec)`

**缺口不需要枚举表，它是从 `B` 和 `vital_ready_ranges` 直接读出来的**：

```
缺口1 = [B,                ready[0].fromSec)
缺口2 = [ready[0].toSec,   ready[1].fromSec)
缺口3 = [ready[1].toSec,   ready[2].fromSec)
...
缺口N = [ready[N-1].toSec, 读取右端)
```

`vital_ready_ranges` 为空时，缺口就是 `[B, 读取右端)`。

**读取右端 = `stableCeiling(now)` = `now - MINUTE_SETTLE_SEC`。** `listRepairGaps()` **只返回 `stableCeiling` 之前的缺口**；`stableCeiling` 之后的秒故意不读——在**补录循环**里，那时读得到但记不了账（5.4），读了也白读，还会让「补到没有缺口为止」这个终止条件永不成立（9.1）。断开前那次大空洞补读（9.3）是循环外的一次性动作，不参与这个终止判据。

**缺口与 ready 区间都是秒级的，不对齐整分钟**，端点直接当 `startSec` 用（设备接受任意时间戳，8.1）。因此一条 ready 区间可能是半分钟的（例如 `[12:00:20, 12:00:28)`），缺口也可能只有几秒——减法在秒上是自洽的，不影响任何推导。

因为 `B` 只能推进到 `ready[0].toSec`，所以**任何时刻只有一个活跃缺口**：

> **缺口 ≡ `[B, ready[0].fromSec)`**（`ready_ranges` 为空时 ≡ `[B, 读取右端)`）

补完这个缺口、推进 `B`、消费掉 `ready[0]` 之后，原来的 `ready[1]` 变成新的 `ready[0]`，下一个缺口**自动**就是 `[B, ready[0].fromSec)`。不需要枚举、不需要排序、不需要存储。

**相邻 ready 区间要合并。** 秒级右端下，两次广播跨分钟判定可能产出 `[12:00:00, 12:00:28)` 与 `[12:00:28, 12:01:00)` 这样首尾相接的两条；写入时如果 `from_sec == 前一条的 to_sec` 就合并，避免行数虚增。

**几秒宽的小缺口不值得单独触发一次读取。** 它们由 8.2 的桥接合并进邻近的读取窗口；若整个缺口组都只有几秒宽（典型成因是连接留下的尾巴），则由 9.4 的广播接续判定处置，不连接。

### 5.3 一个余量、一个边界

```
stableCeiling(nowSec) = nowSec - MINUTE_SETTLE_SEC   -- 记账右端，也是缺口右端
```

`MINUTE_SETTLE_SEC = 10` 秒。以 `now = 12:30:05` 为例：`stableCeiling = 12:29:55`。

`stableCeiling` 是**唯一**的边界，三处共用：

| 用途 | 说明 |
| --- | --- |
| 记账右端 | 允许被写进 `vital_ready_ranges` 的上界（5.4） |
| 缺口右端 | `listRepairGaps()` 的右端（5.2） |
| 分类右端 | `classifyFromBaseline()` 的右端（5.1） |

**除此之外没有第二个边界。** 读取窗口直接取缺口端点和「设备返回的最晚秒」，设备对 `0x3A` 的起始时间没有任何对齐要求（8.1）。

**它的含义是「最后一秒已经等够余量、可以放心记账」**，所以是「`now` 往前 10 秒」，与分钟边界无关（5.1）。

**两条写入路径共用同一个余量。** 它们的余量本质是同一件事——都是「10 秒量级的传输/写入延迟」：

- 广播分类：最后几秒的广播包还在途中。
- 页面记账：最后几秒设备可能还没写好。

若真机测出固件写入延迟确实大于 10 秒，**只需调大这一个常量**，广播分类、页面记账、缺口右端三处一起调整，不会出现两处漂移。它同时是运行时可调的（第 14 节）。

### 5.4 记账规则

「把一段范围记为已记账」只有一个入口：

```
记账 [from, to)：
  to = min(to, stableCeiling(now))
  有效秒        → 数据
  FF / 缺行     → 设备确认「这里没有」
  超出 to 的部分 → 不记账，留在缺口里等它自然稳定（不重读、不确认）
```

`stableCeiling` 之前的范围已经稳定，`FF` 是确定的「设备没有」，可以永久记账。超出它的部分尚无定论，所以既不写 `vital_ready_ranges`、也不当作可读缺口（`listRepairGaps()` 同样封顶在这里），只是等时间走过去。`to` 是秒级的，不向上取整到分钟。

**`advanceBaseline()` 因此不需要任何 clamp**（5.5）：`vital_ready_ranges` 里的每一段右端都不超过 `stableCeiling`，`B` 的上界自动成立。这是把约束下沉到写入路径的好处——约束在数据写入那一刻就成立，而不是事后去拦 `B`。

### 5.5 推进 `advanceBaseline()`

纯表操作，**不查 `ppi_data`，也不做任何 clamp**：

```
若 B 早于 30 天保留窗口 → B 直接跳到保留起点（整分钟对齐），一次性放行
循环：
  B 落在 ready[0] 内（fromSec <= B < toSec）→ B 前进到 ready[0].toSec，消费 ready[0]
  否则               → 停
```

`B` 的上界由 5.4 的记账规则自动保证：写进 `vital_ready_ranges` 的每一段右端都不超过 `stableCeiling`。

**消费 `ready[0]` 要区分整条删除和拆条**：

- `ready[0].toSec <= B` → 整条删除（这一整段都已记账）。
- `ready[0].fromSec < B < ready[0].toSec` → **只改 `from_sec` 为 `B`，不删行**。例如 `B` 推进到 12:30:20 而 `ready[0] = [12:10, 13:00)`，`to_sec` 之后的 40 分钟还没被消费。

**`B` 落在 ready[0] 之前是正常停驻，不是错误。** ready 区间都是秒级的（5.1），`B` 可能停在任意秒上；`[B, ready[0].fromSec)` 就是当前那个唯一的活跃缺口（5.2）。

保留窗口那一步必须**直接跳到保留起点**，不能逐分钟放行：`B` 可能因设备长期连不上而停在几个月前，逐分钟是几万次带表查询的循环。跳到保留起点是一次操作，同时删除早于保留起点的 ready 区间——那些秒永远补不回来了，留着只会在弹窗和启动时被反复遍历。

调用时机：

1. **广播跨整分钟**（正常路径）。分类推进到 `stableCeiling(now)`，把本轮新稳定的秒并进 ready 区间，再推进 `B`。
2. **广播恢复的第一帧**（9.4 的接续判定）。消化连接留下的空洞。
3. **连接结束**（9.3）。
4. **10 分钟自动检查**。兜底，处理广播长时间没来之后的情况。

### 5.6 为什么 ready 区间要单独存

- **`B` 之后「合格但被 `B` 卡住」的分钟有了归属**，否则 `B` 一卡，那些分钟既不在 `B` 里也没被打上任何标记。
- **缺口由减法直接得出**，不需要缺口表，也不需要排序——`ready` 区间天然有序。
- **`advanceBaseline()` 变成纯表操作**，不再逐分钟查 `ppi_data`，更快也更好测。
- **连续区间自动合并**，行数是 O(不合格分钟段数)，不是 O(时间)。`B` 卡一天的代价是 1 条 ready 区间，不是 1440 行。

正常运行时 ready 区间是**瞬态**的：建完立刻被 `advanceBaseline()` 消费掉。它只在 `B` 卡住时驻留——正好是它该起作用的时候。

## 6. App 没开 / 长时间没有广播

因为缺口是推导出来的，而分类永不停止，这个场景不需要任何特殊处理：

1. 重开后 `B` 停在关闭前的时刻，它到现在的全部时间都是「未记账」。
2. `classifyFromBaseline()` 立刻把它们判完。App 关闭期间没有广播 → `ppi_data` 为空 → 整段是不合格 → 整段是缺口。
3. `listRepairGaps()` 直接给出这段缺口，从缺口**末端起读**（8.1），不必等分类追平。
4. 读取后 `B` 推进。

**设备一跳就能确认掉「确实没数据」的整段。** 如果设备在这期间没被佩戴，查 `anchor=now` 向更早翻时首页的 `startSec` 会直接落在缺口起点之前——一次 `0x3A` 就把整段确认成已记账，不会翻几千页。只有设备**真有数据**时才逐页读，而那正是我们要读的。所以「App 关 3 天」的代价：没佩戴 → 一次往返；佩戴了 → 读 3 天的数据（本来就要读）。

## 7. 分钟级上传

上传策略整体替换掉老的「30 条 / 30 秒」批量触发：

- **触发点**：广播 `utc` 跨过整分钟时，上传刚走完的那一分钟。
- **判定与上传是两件事**：先上传该分钟的未上传秒，再做合格判定。**判定依据是本地的 `ppi_data`，不是上传结果**——基准时间描述的是「数据是否收齐」，上传是独立的可重试动作。上传失败时 `uploaded` 保持 0，由重试路径继续消费，不会因为弱网把已经收齐的分钟判成待补。
- 保留 `PPI_UPLOAD_MAX_RECORDS = 300` / `PPI_UPLOAD_MAX_BATCHES = 10` 作为**积压排空**的上限（历史补录落库的秒可能远超一分钟），但正常实时路径每个整分钟只有一批。
- 保留定时兜底，但降级为**重试与排空**：间隔 `UPLOAD_RETRY_INTERVAL_MS = 60 * 1000`，只为消费 `uploaded=0` 的积压和失败重试，不再作为主触发。

## 8. 补数据：一次一个缺口，补完推进再下一个

补录的基本循环：

```
读缺口 [B, ready[0].fromSec)  →  落库 / 确认  →  B 推进，消费 ready[0]  →  下一个缺口
```

因为 `ready[0]` 被消费后 `ready[1]` 变成新的 `ready[0]`，**下一个缺口自动浮现**，不需要重新枚举。所以「一直是 `B` 到第一条数据的开始时间是缺口」。

### 8.1 读取方向：缺口内从后往前

两方面不是一回事，不要混：

- **缺口顺序**：从 `B` 往前走——先补第一个缺口。
- **缺口内读取方向**：`anchor` 取缺口的**末端**，`direction = 0` 向更早翻页，翻到缺口起点。

这就是文档第 8 节标题「两分钟倒序读取」讲的 `0x3B` 方向。大缺口（App 关了 3 天）因此是从**最新端**开始读的，最新数据最先落库。

**`anchor` 取缺口末端的原始秒，不做任何对齐。** 设备的 `0x3A` 收的就是裸的 UTC 秒（[protocol.ts:296-312](.cool/store/device/protocol.ts#L296-L312)），**任意时间戳都行，设备没有「必须整分钟」的要求**。对齐是我们自己发明的约定，代价是丢掉最多 59 秒的可读窗口——对 9.3 那种几十秒的连接空洞尤其明显（对齐后窗口可能直接变空）。现有代码的历史游标本来就是设备返回的 `page.startSec`（任意秒），从来没有对齐过，所以这里也不需要引入。

**读取窗口的右端**取「缺口末端」与「设备返回的最晚秒」的较大值，同样不向上取整。`minutes = 2` 是**每页步长**（翻页时向更早走 2 分钟），不是「窗口必须对齐到 2 分钟」——两者不是一回事。

### 8.2 桥接：把碎缺口并成一条链路

纯「一次只补一个缺口」在丢包场景下会碎片化。例如 12:05 和 12:07 两分钟不合格、12:06 合格，则 `ready[0] = [12:06,12:07)`，会拆成两个缺口、两条 `0x3A` 链路。丢包率高时（30% 丢包 → 约一半分钟不合格）一小时能拆出几十条链路。

所以实际读窗口 = **第一个缺口，向前桥接跨过的短 ready 区间**，沿用文档的 `HISTORY_GATT_READ_BRIDGE_SEC = 120`：

```
读窗口 = [B, 末端)
末端 = 从 ready[0].fromSec 起，只要「下一个缺口的宽度」+「中间 ready 区间宽度」都在 120 秒内就继续向前合并
```

桥接跨过的秒本地已有，不重复入库。读完后 `B` 一并推过整个窗口。这等价于「相距 120 秒内的缺口合成一组」，但表述仍从 `B` 出发，仍然只有一个活跃缺口组 —— 不破坏「一次一个缺口」的模型。

### 8.3 读取链路与收尾

- **范围**：一次连接把 `listRepairGaps()` 的缺口全部处理完（带 8.2 的桥接）。
- **连接没有时长上限**：需要补的缺口就一直补，补到完成再断开。原来「120 秒必须断开把通道还给广播」的约束由第 9 节取代——超出宽限值的空洞在断开前读一次补回（9.3），小空洞由广播接续消化（9.4），所以长连接不再制造遗留缺口。
- **读取方式**：沿用整组一次 `0x3A`、之后连续 `0x3B`，每页先落库再续读。每页落库后：
  - 有效秒写入 `ppi_data`（`uploaded=0`）。
  - 按 5.4 的记账规则把该页可确认的范围并入 `vital_ready_ranges`——**只记到 `stableCeiling`；超出部分不记账**，等它自然稳定。
- **收尾**：
  - 设备返回段早于整个缺口（`page.startSec < 缺口.from_sec`，或 `startSec=0`）→ 该缺口设备无数据，整段按 5.4 记账。这是设备关机 / 未佩戴的正常路径，**不是失败**，继续读下一组。
  - 响应结构截断（秒数超出声明、残缺 6 字节记录）→ 视为链路错误，中止本轮。
  - 超时 / 发送失败 → 中止本轮。已提交的页面保留，剩余缺口留在原地，下一次连接重来。
- 补录落库后调用 `scheduleUpload()` 异步消费，不阻塞 GATT 释放。

**缺口读完之后还有一次可能的读取：9.3 的大空洞补读。** 仅当 `tail > BROADCAST_RESUME_GRACE_SEC` 时执行，方向 `direction=0`、anchor 取 `disconnectAt`（与缺口补录同方向），在 `advanceBaseline()` 之后、断开之前。缺口读不到任何东西（没有缺口）**不代表没有活**——恰恰是没有缺口的那一轮，连接自己造成的空洞才最容易漏给下一次连接。小空洞由 9.4 的广播接续消化，大空洞由这一次读取消化，两者必居其一。

**失败退避由连接间隔天然提供。** 缺口不落库，所以没有 `retry_at` / `attempts`。读取失败后缺口仍在，下一次连接至少 10 分钟后才来，自然重试。

补录完成后不需要额外的「核验」任务：`B` 自己会重新推进，合格的分钟自动被吸收进基准时间。

### 8.4 广播缺秒：记录、合并，等下一次连接一起补

广播缺行只有一种成因：**那一秒的广播帧没收到**（空口丢包 / 系统漏扫）。设备不佩戴也会广播，那只是指标全 0，仍然会落一行（第 7 节）。所以缺行 ≠ 设备没记——**设备历史里大概率有这一秒，连一次就能补回真数据**。

即便如此，结论仍然是**不立刻连接**，把它交给 5.2 的缺口推导和 9.7 的自动检查：

- **代价不划算，而且代价几乎与缺口宽度无关。** 一次连接的开销固定在停扫描 / 直连 / 初始化握手 / 断开静默（350ms + 120ms）/ 重启扫描这几步上，是**数秒**量级；而补 1 分钟缺口只要 1 页、约 1.45 秒。为几秒的丢包付数秒的连接开销，并且这段时间广播是停的，收益是负的。
- **延迟没有用户可见的代价。** 实时展示走的是实时广播流，不是 `ppi_data` 补录；补一秒钟的早晚，只影响历史数据的补齐和上传时点，不影响用户看到的任何东西。
- **设备是历史的权威，晚补不丢数据。** 秒数据在设备 flash 里，缺口不落库也不会过期；5.5 的 30 天保留窗口是唯一的时间约束。
- **`B` 停驻本来就是预期行为**（第 2 节）。`B` 卡在失败的那一分钟，后面合格的分钟堆在 `vital_ready_ranges` 里等它（5.6），行数是 O(失败段数)，不是 O(时间)。丢包率高时 8.2 的桥接会把 120 秒内的碎缺口并成一条链路，一次连接读完。

**只有两种情况升级为加急连接**（绕过 9.7 的 10 分钟间隔，但与校时/事件的加急不同，仍受一个更短的间隔约束）：

| 触发 | 判据 | 为什么值得 |
| --- | --- | --- |
| 广播静默后恢复 | 长时间无绑定广播后 `markBroadcastRecoveryOk()` 被触发 | 这是「App 被后台冻结 / 走出范围」的确切信号，积压已确定存在，检查一次几乎零风险 |
| 缺口宽度 | 单个缺口 ≥ `HISTORY_GATT_READ_BRIDGE_SEC`（120 秒），**且广播当前在线** | 宽缺口不可能由零星丢包造成（是空口级故障）；补它要读的秒多，连接开销的边际占比最低，且拖久了会滚大 |

**「广播当前在线」这个前提不能省。** 广播离线时出现缺口是必然的（没有广播源），此时加急连接会退化成每隔几分钟连一次、每次都把广播再掐掉——补缺口的同时制造新缺口。广播离线期的积压应当**等广播恢复**后一次性处理，那正是上表第一行的触发。

**不要把「缺口总秒数」单独作为触发。** 它无法区分「空口丢包」（设备有数据，值得连）和「设备没记」（连了也只会拿到全 `FF`，白跑一趟），会退化成对零星丢包的频繁连接。宽度触发之所以能用，是因为它能区分空口级故障和零星丢包；总秒数触发不能。

**加急连接的最小间隔单独设一个更短的值**（不要复用 9.7 的 `MIN_CONNECT_INTERVAL_MS`，也不要完全放开）。完全放开会让「广播质量差 → 频繁连接 → 广播更长时间停摆」形成恶性循环；而完全复用 10 分钟又让加急失去意义。真机调参时这个值只需要保证「一次加急连接的收益大于它自己造成的空洞」——按 9.6 的 83 倍实时，只要缺口宽度大于连接开销的数十倍就成立。这个值运行时可调（第 14 节）。

## 9. 连接生命周期与广播接续

这一节是整套设计的核心，目标是两条，顺序不能反：

1. **尽量减少连接。** 连接期间广播是停的，所以每一次连接都在制造缺秒。能靠广播读到的数据，绝不靠连接；连接只用于广播给不出的东西（设备 flash 里的历史、事件、校时）。
2. **连接一旦发生，它留下的缺秒必须在同一轮消化掉，不能转交给下一次连接。** 否则「连接 → 缺秒 → 下一次连接 → 又缺秒」会自己咬住自己，退化成反复连接——这正是要避免的形态。

第 1 条否掉了两种做法：为几秒的广播丢包立刻连接（8.4），以及为 1~2 页的小连接空洞多做一次设备补读（9.3）。第 2 条落在 9.4 的广播接续判定上——它是把循环断开的那一步。

**连接不再设时长上限。** 一次 flush 需要读多久就读多久，补到完成再断开。

只有一个边界：

```
stableCeiling = now - MINUTE_SETTLE_SEC   -- B 能推到哪、缺口右端
```

**`direction=1` 实测异常，全程只用 `direction=0`。**

### 9.1 读取范围封顶在 `stableCeiling`

**`listRepairGaps()` 只返回 `stableCeiling` 之前的缺口，读取也据此封顶。`stableCeiling` 之后的秒在补录循环里故意不读。**

这条约束是必需的，不加会导致死循环：

```
连接期间补了 40 分钟，读完后 B 只推进到 stableCeiling（最后 10 秒还没稳定）
listRepairGaps() 再查 → 缺口 = [stableCeiling, now) 非空
  → 再读一次 → 取到同样的数据 → 记账结果不变（仍受稳定余量限制）
  → 缺口仍非空 → 再读 → 死循环
```

`listRepairGaps()` 永不排空，「补到没有缺口为止」这个终止条件就不成立。根因是把「最后的秒还没稳定、不能确认 `FF`」和「这段是待读缺口」混成了一件事——后者会把前者反复喂回读取循环。这两件事必须分开：

- **`stableCeiling` 之前的缺口**：可以记账，值得读。
- **`stableCeiling` 之后的秒**：读得到但记不了账。**循环**（9.3 的补录循环）不能碰它，否则永不排空；但**断开前那次一次性补读**要覆盖它——那是一次动作，不参与「补到没有缺口为止」的判据，多读的部分按 5.4 不记账，留在缺口里等它自然稳定。

### 9.2 容差只有 8 秒，宽限值不是容差

连接的缺秒落在分钟容差内时，分类会判它合格、`B` 直接推过去：

```
连接 12:00:00~12:00:05，这 5 秒不会经广播进来
12:01:10 广播分类判 [12:00,12:01)：缺 5 秒
  → 5 ≤ 19 且最长连续缺失 5 < 9 → 合格 → B 直接推到 12:01:10
```

**容差的第二个条件（最长连续缺失 < 9 秒）是硬约束**，而连接空洞是连续的，所以只有 **≤ 8 秒** 的空洞才真能被容差吸收。9.4 的宽限值 60 秒远超这个数——它对 9~60 秒的空洞执行的是**强制推进**，那几十秒的真数据被有意放弃。这一点在 9.4 里说明，**不要把宽限值理解成「容差范围内」**。

另外两条边界要注意：

- 判据看的是**空洞宽度**，与连接总时长无关（9.3 用 `tail > BROADCAST_RESUME_GRACE_SEC` 判定，不用总时长）。
- 一条连接里停广播 / 连设备 / 恢复广播可能有**多段**间断，容差只看最长的那一段。

分界线就是 9.3 的 `BROADCAST_RESUME_GRACE_SEC`：8 秒以内由容差自然吸收，8 秒到宽限值之间强制放弃，超过宽限值读设备把真数据拿回来。

### 9.3 大空洞：断开前读一次设备

**这是整套设计里唯一一次「为连接自己的尾巴读设备」的读取。** 连接期间广播停了，广播又不携带历史秒，所以这段空洞只有 `0x3A`/`0x3B` 能拿回来。它是 9.4 接续判定的兜底：小空洞靠推定消化，大到会丢真数据的空洞靠这一次读取消化。

**判据是连接留下的空洞宽度，不是连接时长**——留不留缺口取决于空洞形状：连接 12:00:20~12:00:30 只跨 10 秒，却让 `[12:00,12:01)` 连续缺 10 秒 → 不合格 → 真缺口；反过来，一条 3 分钟的连接如果中途广播短暂恢复，空洞反而可能很小。

```
连接开始前（停广播那一刻）：记录 holeFrom = 停广播时刻的整秒
执行本轮所有任务（校时 / 事件 / 补录）
  补录：读完 listRepairGaps() 的全部缺口（已封顶在 stableCeiling）
advanceBaseline()
决定断开：记录 disconnectAt，tail = disconnectAt - holeFrom
  ├─ tail > BROADCAST_RESUME_GRACE_SEC
  │    空洞太大，推定为空会丢掉真数据（用户在连接期间是戴着设备的）
  │    读一次：direction=0, anchor=disconnectAt，翻到 <= B 或设备无数据即停
  │    每页落库 + 按 5.4 记账（超出 stableCeiling(断开时刻) 的部分不记账）
  │    advanceBaseline()
  └─ tail <= BROADCAST_RESUME_GRACE_SEC
       1~2 页的小空洞，不值得为它多读一轮
       不读。B 停在这里，整段交给 9.4 的广播接续
断开，恢复广播
```

三个取值的要点：

- **`holeFrom` 在停广播那一刻取，不能在 `connectedAt` 取。** 停广播从 `switchToConnectMode()` 的 `stopBluetoothSearch()` 开始，比 `connectedAt` 早，用后者会漏掉这段秒。放置位置见 9.7。
- **右端按断开时刻重算，不是取开始时的值。** 补录期间时间在走，断开时算出的 `stableCeiling` 比开始时大得多。
- **`anchor` 取 `disconnectAt` 的原始秒，不对齐**（8.1）——对齐会把窗口末端往回推，几十秒的空洞可能直接被推空。

**为什么大空洞必须读。** 补录驱动的连接可能长达几分钟，用户在这期间是**戴着设备的**——那段秒在设备 flash 里有真数据。不读就只剩 9.4 的强制推进，等于把真数据永久丢掉。

**为什么小空洞不读。** 1~2 页的读取要额外几秒 GATT 占用，而那段时间又在制造新的空洞；更关键的是，它买来的只是「`B` 到位」的结果，而 9.4 的接续判定在同样的小空洞上能免费给出同样的结果。省掉这一次读取，正是「尽量减少连接、尽量用广播」的一条具体落实。代价是那几十秒被有意放弃——明确写在 9.4。

**方向是 `direction=0`（向更早翻页），`direction=1` 实测会异常、不使用**，与缺口补录方向一致。

**`B` 必须在断开时推到当前时间。** 这是 9.4 的前提，也是整套设计能否收敛的关键——`B` 留在 `disconnectAt` 之前，下一次自动检查就会把这段当成缺口、再拉起一整条连接去补，而那次连接又制造新的缺秒，于是反复连接。落实方式有两种，二选一，不能都不做：

1. `tail > BROADCAST_RESUME_GRACE_SEC` → 上面的设备补读把 `B` 直接推到 `stableCeiling(disconnectAt)`。
2. `tail <= BROADCAST_RESUME_GRACE_SEC` → `B` 停在 `holeFrom`，由 9.4 在广播恢复后一次性推到 `stableCeiling(T0)`。

### 9.4 广播接续判定：这是收敛的关键

**连接一定会留下缺秒，而连接又只由「有缺口」触发——所以如果不把连接留下的那段缺秒就地消化掉，下一次检查就会再拉起一条连接，那条连接又留下新的缺秒。这是一个会自己咬住自己的循环，表现就是反复连接。断开连接必须断开这个循环，而不是把缺秒转交给下一次连接。**

消化手段就是广播：广播恢复后的第一帧 `T0` 一到达，就判定 `[B, T0)` 这段连接空洞该不该记账。

```
广播恢复后收到第一帧（utc 可信）：
  gap = T0 - B
  ├─ gap <= BROADCAST_RESUME_GRACE_SEC
  │    整段按「确认无数据」推进：B → stableCeiling(T0)，并记账到 vital_ready_ranges
  │    不读设备、不连接
  └─ gap 更大
       走 9.3 的设备补读（下一次连接时处理），或按 5.4 正常判定
```

**这不是「容差吸收」，是「有意丢掉这段秒、强制推进 `B`」。** 分钟容差的第二个条件是**最长连续缺失 < 9 秒**，而连接空洞是**连续的**。所以：

- 空洞 **≤ 8 秒** → 落在容差内 → 该分钟照样判合格 → 推定和真读结果确实相同。
- 空洞 **≥ 9 秒** → 该分钟**不合格** → 若推定为空，这一分钟会被判成缺口、`B` 推不过去；此时推进 `B` 就是在**放弃这几秒的真数据**。

所以 `BROADCAST_RESUME_GRACE_SEC` 取 60 秒时，它对 9~60 秒的空洞执行的是**强制推进**：把设备里真实存在的那几十秒当作「确认无数据」记账，永久放弃。这是一个**有意的取舍**，理由如下：

- 反过来的代价是**反复连接** —— 每条连接掐掉几分钟广播，丢掉的是**实打实的几十上百秒真数据**，远大于被放弃的这几十秒。
- 被放弃的这几秒是连接中断窗口的产物，不是用户的真实生理记录缺口；用户看到的实时展示走广播流（恢复后立刻正常），不依赖 `ppi_data` 的历史回补。
- 如果希望这几秒一个都不丢，唯一办法是 9.3 的阈值收到 8 秒 —— 那意味着**几乎每次连接都要多做一次设备读取**，正是要避免的形态。两者不可兼得，这里选择减少连接。

**取值。** 建议 60 秒。它的作用不是「覆盖容差」（容差只覆盖 8 秒），而是划定「多大的空洞值得为它多读一次设备」。这个值运行时可调（第 14 节）：

| 取值 | 后果 |
| --- | --- |
| 太小（如 10 秒） | 连接的小空洞几乎全部推给设备补读，每条连接多跑一轮 → 反复连接 |
| 60 秒（建议） | 一分钟以内的连接中断一律放弃那几十秒、强制推进；超过才读设备 |
| 太大（如 300 秒） | 放弃的真数据变多（一次连接丢几分钟的数据），且那几分钟设备里明明有 |

**这个判定必须在广播恢复路径上，不能在定时检查里。** 定时检查跑的时候广播可能已经稳定了很久；而且定时检查的入口是「列缺口」，那时这段空洞已经变成缺口、必然触发连接 —— 判定就晚了。所以要挂在 `markBroadcastRecoveryOk()` 或广播落库路径上，判定要在缺口推导**之前**发生。

**判定为「接续」之后要记账，不能只推 `B`。** 按 5.4 的规则把 `[B, stableCeiling(T0))` 并入 `vital_ready_ranges`，`B` 再 `advanceBaseline()` 推过去。只推 `B` 不记账会让 `advanceBaseline()` 找不到对应的 ready 区间而停在原地（5.5 的循环是「B 落在 ready[0] 内就前进」，没有区间就不动）。

### 9.5 残余部分与收敛

`B` 推到接续判定的右端（`stableCeiling(T0)`）之后，剩下的几十秒由广播正常路径推进：秒级数据正常进来，下一分钟走完并过 `MINUTE_SETTLE_SEC` 时分类判定合格，`B` 就推到那里。

所以「连接结束时把 `B` 推到当前时间」的完整语义是两段：

1. **断开时**：`tail > BROADCAST_RESUME_GRACE_SEC` 由设备补读推到 `stableCeiling`；否则 `B` 停在 `holeFrom`。
2. **广播恢复后**：9.4 的接续判定把 `[B, stableCeiling(T0))` 一次性记账推进——不管 `B` 停在哪，这一步之后 `B` 都到位了。

**收敛靠的是接续判定，不是补读。** 9.3 的补读是「大空洞不丢真数据」的保险，9.4 的接续判定才是「不反复连接」的机制。两者都要有：只有补读，小空洞会让 `B` 落后、触发下一次连接；只有接续判定，大空洞的真数据会被永久丢掉。

**收敛的判据是「连接留下的空洞在同一轮消化掉」，不是「`B` 等于 `now`」。** 后者不可能达到：`stableCeiling` 之后的最后 10 秒尚未稳定、本轮不记账，只能由广播在它走完余量时吸收。

### 9.6 为什么这套能收敛

**广播在线时**：`B` 由分类推进到 `stableCeiling ≈ now - 10s`，即每次分类都在追，没有累积。

**广播离线时**（App 后台/关闭）：`ppi_data` 不增长，缺口会累积，但此时没有广播要保护，连接可以一直补到 `stableCeiling`，补完断开放广播。

**连接空洞**：这是唯一会自咬的形态，由 9.4 的接续判定断开——连接留下的小空洞在广播恢复的第一帧就地推定消化，`B` 推进、缺口消失、不再触发下一次连接。**「连接 → 缺秒 → 连接」的循环因此不成立。**

**大空洞的设备补读**：补 `T` 秒要占用 `T/83` 秒（GATT 每页 2 分钟数据 1.45 秒，约 83 倍实时），这 `T/83` 秒又留下新的空洞，再读回又要 `T/83²` 秒……几何级数求和约 `1.012T`，额外开销约 **1.2%**。这个尾巴由 9.4 兜住，不跨连接累积。

### 9.7 连接最小间隔

`MIN_CONNECT_INTERVAL_MS = 10 * 60 * 1000`。自动检查按这个间隔跑；一轮连接把积压补完，下一次连接至少 10 分钟后。这也顺带提供了缺口读取失败的天然退避（缺口不落库，没有 `retry_at`）。加急任务（校时、广播 `eventSeq` 变化触发的事件读取、以及 8.4 的两类加急缺口）**不受这个间隔限制**，仍立即连接；否则设备一有新事件就要等 10 分钟。加急缺口连接另有一个更短的间隔，见 8.4。

**这个间隔同时是「缺口要等多久才被补」的上界**，也是 9.4 接续判定存在的第二个理由：连接留下的空洞如果不在广播恢复时就地消化，`B` 会一直落后，下一次自动检查立刻又把这段当缺口、再拉起一条连接，循环就此成立。接续判定把这段压到同一轮内闭环。

放置位置：这段逻辑属于 `DeviceGattScheduler.flush()` 的收尾，紧挨现有的 `switchToBroadcastMode()`，因为停广播 / 连设备 / 恢复广播都由 flush 统一负责。`holeFrom` 在 `switchToConnectMode()` 内、`stopBluetoothSearch()` 之后取，不能放在 `flush()` 开头——那时广播可能还在跑。

## 10. 读取日志

缺口不落库之后，日志成了唯一的观测手段，必须能回答「这次连接读了什么、补了多少、`B` 推到哪、还剩多少」。四层日志：

**连接层**——回答「这次连接值不值」

```text
[BOOM-HISTORY] 开始补录: B=..., 缺口组=..., 缺口秒=..., 连接开始=..., 计划断开=...s
[BOOM-HISTORY] 补录结束: B=...->..., 已补组=..., 失败组=..., 落库秒=..., 剩余缺口=..., 剩余秒=..., 连接时长=...s
[BOOM-HISTORY] 本轮空洞补读: holeFrom=..., disconnectAt=..., tail=..., 窗口=...~..., 页数=..., 落库秒=..., B=...->...
[BOOM-HISTORY] 本轮空洞小，跳过补读: holeFrom=..., tail=..., B=..., 交由广播接续
[BOOM-ADV] 广播接续: T0=..., B=..., gap=...s, 宽限=...s, 决策=推进/交给设备, B=...->...
```

`广播接续` 这一行是「没在反复连接」的直接证据，也是这套设计的健康指标。`决策=推进` 表示连接留下的空洞已就地消化、不会触发下一次连接。**如果这一行反复出现 `决策=交给设备`，说明宽限值取小了**，连接的小空洞一直被推给设备补读，等于每条连接都要多跑一轮 —— 那正是要避免的形态。反过来，`本轮空洞补读` 这一行应该只在连接中断较久（补录驱动的长连接）时出现，**每次连接都出现说明 `BROADCAST_RESUME_GRACE_SEC` 取小了**。

`B=...->...` 是整轮的唯一结论。`剩余缺口` 与 `剩余秒` 直接来自 `listRepairGaps()` 的重算，是「还有多少活」的确切数字。

**缺口组层**——回答「这一组读到哪、为什么停」

```text
[BOOM-HISTORY] 缺口组开始: n/m, window=...~..., 缺口秒=..., bridge秒=..., anchor=..., minutes=2, direction=0
[BOOM-HISTORY] 缺口组结束: n/m, window=...~..., status=..., pages=..., 落库=..., 已记账=..., 最早未读起点=..., elapsed=...s
[BOOM-HISTORY] 缺口组失败: n/m, window=..., status=..., pages=..., message=...
```

`缺口秒` 与 `bridge秒` 分开打印：前者是真正要补的秒，后者是合并相邻缺口时跨过的已有秒。两者一起看才知道合并省了多少次往返。

**页层**——默认不打印，只在异常和有诊断需要时打印

```text
[BOOM-HISTORY] 页: startSec=..., n=..., 秒记录=..., 有效秒=..., 无效秒=..., 全FF秒=..., 目标剩余=...s
[BOOM-HISTORY] 页落库: page=..., 新增秒=..., 覆盖旧占位=..., 记账=...~...
[BOOM-HISTORY] 设备无数据确认: window=...~..., page=..., confirmed秒=...
[BOOM-HISTORY] 页截断，中止本轮: page=..., 声明=..., 实际=...
[BOOM-HISTORY] 页未向更早推进，中止本轮: page=..., 上页=...
```

页层是「补录卡在某一段」的唯一线索：`全FF秒` 全是 60 说明设备确实没记这段；`有效秒=0` 但不是全 FF 说明解码有问题；`页未向更早推进` 说明固件在空转。

**诊断字段**（固定在每页摘要里，便于 grep）：页的 `startSec`、`n`、实际秒记录数、有效 / 无效 / 全 FF 计数、以及**本页对 `vital_ready_ranges` 的贡献**。最后一项是核对「记账是否按预期推进」的直接证据——记账错了，`B` 就会停在错误的位置。

所有日志走 `.cool/service/logger.ts` 进诊断日志，不 `throw`、不只用 `console`。

## 13. 日志检查清单

```text
[BOOM-BASE] 分类完成: 未记账=...s, 新记账=...~..., 新缺口=...~..., 分类右端=..., 用时=...ms
[BOOM-BASE] 分钟不合格: minute=..., missing=..., 最长连续缺失=..., 阈值=19/9
[BOOM-BASE] 基准推进: B=...->..., 消费ready区间=..., 原因=ready/expired
[BOOM-BASE] 基准停驻: B=..., 阻塞分钟=..., 缺口组=..., 缺口秒=...
[BOOM-BASE] 刻度: now=..., stableCeiling=..., B=...
[BOOM-BASE] 加急连接判定: 缺口宽=...s, 广播在线=..., 静默恢复=..., 决策=...
[BOOM-UPLOAD] 分钟上传: minute=..., count=..., ok=...
```

- `分类完成`：每轮判了多少秒、产出多少缺口。**分类永不停止是设计前提**，这一行长期不动说明 `ppi_data` 查询或区间算术出了问题。`分类右端` 就是 `stableCeiling`，便于核对它是否等于 `now - MINUTE_SETTLE_SEC`。
- `分钟不合格`：哪一分钟因为什么判失败。`missing` 与 `最长连续缺失` 直接对应第 3 节的两个阈值，`阈值=19/9` 把判定线一并打出来，不用回翻代码。
- `基准推进` / `基准停驻`：`B` 为什么动或不动，后面还积压多少缺口。
- `刻度`：三个时间值一起打印。**`B` 与 `stableCeiling` 的差距是排查「`B` 落后」的第一现场**——两者都是秒级的、不整分钟对齐，所以正常情况下 `B` 就贴着 `stableCeiling`（差值在秒的量级）。`B` 明显小于它说明有真缺口卡在前面。
- `加急连接判定`：只在加急路径上打印，回答「为什么现在连了」。`缺口宽` 与 `广播在线` 是 8.4 的两个判据，`决策` 取 `connect` / `wait`。**这行频繁出现（比如每几分钟一次）说明宽度阈值取小了**，退化成对零星丢包的频繁连接，广播停摆时间会明显上升。
- `广播接续`：每次广播恢复的第一帧打印一次，回答「连接留下的空洞消化了没有」。`决策=推进` 是健康状态；`决策=交给设备` 反复出现说明 `BROADCAST_RESUME_GRACE_SEC` 取小了。
- **判断「是不是在反复连接」看两条曲线的组合**：`[BOOM-SCHED] 开始执行队列` 的间隔应当稳定在 `MIN_CONNECT_INTERVAL_MS` 附近；如果明显更频繁（尤其伴随 `加急连接判定` 或反复的 `决策=交给设备`），说明有某个缺口在源源不断地触发连接——先看 `广播接续`，再看 `加急连接判定`。

连接检查点与四层补录日志见第 9、10 节。

## 14. 运行时可调参数

这套设计里有四个数值只有真机数据才能定，而反复改代码重装才能调一次是不可接受的。所以它们**不写死在常量里**，走运行时配置：

```ts
// .cool/bluetooth/history/tunables.ts —— 新增
// 默认值 = 代码里的常量；有本地覆盖就用覆盖值；没有就返回默认值。
// 所有读取点都走这里，不允许别处直接引用默认常量。
export type HistoryTunables = {
	minuteSettleSec: number;         // 默认 10
	broadcastResumeGraceSec: number; // 默认 60
	bridgeSec: number;               // 默认 120
	urgentGapIntervalMs: number;     // 默认 待定
};

export function getHistoryTunables(): HistoryTunables;
export function setHistoryTunable(key: keyof HistoryTunables, value: number): void;
export function resetHistoryTunables(): void;
```

**持久化用 `.cool/utils/storage.ts` 的 `storage.set(key, value, 0)`**，key 前缀 `boom_history_tune_`。**必须持久化**：这些是被长期观测的量，App 重启就丢会让「调一次、观察几天」变得不可能。`resetHistoryTunables()` 清掉全部覆盖、回落到默认值。

**读取点必须是调用时读，不能模块加载时快照。** 这些是长驻服务（`sync` / `broadcast` / `gatt-scheduler`），常量一旦在模块顶层读进变量，改了要重启 App 才生效，那就失去了可调的意义。每处用到的地方调用 `getHistoryTunables().xxx`。

| 位置 | 内容 |
| --- | --- |
| `pages/device/test.uvue` | 新增第 7 个弹窗入口「补录参数」 |
| `pages/device/components/HistoryTunePopup.uvue` | **新增**。四个数值的输入框 + 当前生效值（含「默认 / 已覆盖」标记）+ 重置按钮 + 当前日志 |

理由：这些是诊断/调参用的，不是用户功能，不该出现在设置页；测试页已有六个同类全屏弹窗入口（[test.uvue:117-171](pages/device/test.uvue#L117-L171)），加第 7 个是同构的做法。**而且调参时正在看的日志就在手边**——这个弹窗的用途是「改一个值 → 看 `[BOOM-ADV] 广播接续` 的 `决策` 列 → 再改」，把日志和输入框放同一屏是有意的。

**覆盖时要打日志**，否则「为什么行为和文档不一致」会很难查：

```text
[BOOM-TUNE] 参数覆盖: key=..., 默认=..., 生效=...
[BOOM-TUNE] 参数已重置: key=...
```

### 每个参数调错了会怎样

| 参数 | 默认 | 调小的后果 | 调大的后果 |
| --- | --- | --- | --- |
| `minuteSettleSec` | 10 秒 | 把设备还没写完的秒当成「确认无数据」，记错 | `B` 落后 `now` 更多，但更安全 |
| `broadcastResumeGraceSec` | 60 秒 | **反复连接**（小空洞被推给设备补读） | 连接留下的真数据被有意放弃得更多 |
| `bridgeSec` | 120 秒 | 碎缺口合并得少，读取链路变多 | 单次链路变长，一次连接占 GATT 更久 |
| `urgentGapIntervalMs` | 待定 | 广播质量差时频繁连接，恶性循环 | 加急失去意义，宽缺口久拖不补 |

`MINUTE_SETTLE_SEC` 是四个里唯一会造成**数据错误**（而非效率损失）的，所以它的默认值改动要格外谨慎。

## 15. 变更记录

方案在讨论中经历了几次结构性调整。这里只记**决定与理由**，推导过程见正文对应章节。

### 2026-09-15 定稿

| 决定 | 理由 |
| --- | --- |
| 删除 `ACCOUNT_MARGIN_SEC = 120`，两条写入路径统一用 `MINUTE_SETTLE_SEC = 10`（5.3） | 那个 120 秒是从老流程 `historyStableBefore` 直接搬来的**未经验证的猜测**（老文档自己写着「尚无真机时延数据支撑」）。保留它只有一个后果：`B` 长期落后当前时间 2 分钟，而「每次连接都把基准推到尽可能新」正是这套设计的核心目标。两条路径的余量本质是同一件事，没有理由用两个值 |
| 读取范围封顶在 `stableCeiling`（9.1） | 原设计的 `listRepairGaps()` 读到最后 `now`，但记账受余量限制，最后一分钟读得到却记不了账 → 缺口永不排空 → 死循环。根因是把「最后的秒还没稳定、不能确认 `FF`」和「这段是待读缺口」混成了一件事 |
| 4 张表减到 2 张：删除「待补窗口表」与「设备确认表」（第 4 节） | 缺口由 `B` 与 `vital_ready_ranges` 直接推导，不落库；设备确认无数据并进 `vital_ready_ranges`。代价是读取失败没有持久化的 `retry_at` / `attempts`，改由「连接最小间隔 10 分钟」天然提供退避 |
| 缺口推导改为「一次一个活跃缺口」（5.2） | `B` 只能推进到 `ready[0].toSec`，所以任何时刻只有 `[B, ready[0].fromSec)` 一个活跃缺口；补完推进后 `ready[1]` 顶上来，下一个自动浮现。不需要枚举、排序或存储 |
| 删除「已分类游标 `C`」 | 引入 `C` 是为了修「`B` 卡住时每轮重扫同一段」的真 bug。换成「分类幂等 + 无单轮上限」后不再必要——分类每次从 `B` 走一遍，已记账分钟直接跳过，多走的成本只是内存算术 |
| 删除连接时长上限 `GATT_FLUSH_BUDGET_MS`（120 秒）与 `listBudgetedTasks()`（8.3） | 原上限的理由是「补录期间广播是停的，上限必须有界」。取消后长连接会留下长空洞，靠第 9 节收回：补 `T` 秒空洞要 `T/83` 秒（约 83 倍实时），新留下的 `T/83` 秒读回又要 `T/83²` 秒，几何级数求和约 `1.012T`，额外开销约 1.2%，不发散 |
| 删除 `scan` / `verify` 两类中间态任务与 6 小时有界调和 | 老流程切 6 小时是为了限制「遍历 30 天 86 万个时间戳」，新分类只查未记账分钟，该理由不成立 |
| `advanceBaseline()` 去掉统一 clamp（5.4、5.5） | 早先用 `settledTo(nowSec)` 把 `B` 拦在「最后一个已过余量的整分钟」，那是**错误的位置**：未稳定的范围一旦写进 `vital_ready_ranges`，数据就已经错了，事后拦只是延后暴露。约束必须下沉到写入那一刻，`B` 的上界才自动成立 |

**未变的部分**：分钟合格判定的两个阈值（缺失 < 1/3、无连续缺 9 秒）、分钟级上传、缺口内从后往前读、桥接 `HISTORY_GATT_READ_BRIDGE_SEC = 120`、连接最小间隔 10 分钟、30 天保留窗口——这些从讨论开始就没有改动。

### 2026-09-16 修订：广播接续判定，切断「连接 → 缺秒 → 连接」的循环

| 决定 | 理由 |
| --- | --- |
| 新增 9.4 广播接续判定 | 连接一定会留下缺秒，而连接又只由「有缺口」触发——不在同一轮消化就会自己咬住自己，表现是反复连接。消化手段是广播：恢复后第一帧 `T0` 到达时，若 `T0 - B <= BROADCAST_RESUME_GRACE_SEC` 就整段按「确认无数据」记账并推进 `B` |
| 9.3 从「无条件补读」改为「仅大空洞补读」 | 判据改为空洞宽度 `tail > BROADCAST_RESUME_GRACE_SEC`，不是连接时长——留不留缺口取决于空洞形状。小空洞不读，因为 9.4 能免费得到同样的 `B` 落点，多读一轮只是多占几秒 GATT 又制造新空洞 |
| 新增 8.4：广播缺秒不立即连接 | 缺行只可能来自空口丢包（不佩戴也会广播，指标全 0 而已），设备历史里大概率有真数据。但连接开销固定为数秒，补 1 分钟缺口只要 1.45 秒，收益为负；实时展示走广播流不受影响；`B` 停驻本就是预期行为 |
| 加急连接只保留两类触发 | **广播静默后恢复**（`markBroadcastRecoveryOk()`，积压已确定存在），以及**缺口宽度 ≥ `HISTORY_GATT_READ_BRIDGE_SEC` 且广播当前在线**。「广播在线」这个前提不能省：广播离线期加急连接会边补边掐广播，退化成恶性循环。明确排除「缺口总秒数」作为触发——它无法区分「空口丢包」与「设备没记」 |

### 2026-09-16 修订（二）：`stableCeiling` 去掉整分钟对齐，`B` 与读取全部改为秒级

| 决定 | 理由 |
| --- | --- |
| `stableCeiling` 从 `floor((now - MINUTE_SETTLE_SEC)/60)*60` 改为 `now - MINUTE_SETTLE_SEC`（5.3） | 取整分钟会产生死区，直接破坏 9.4 的接续判定：`now = 12:00:38` 时整分钟版本给出 `12:00:00`，若 `B = 12:00:20` 则分类右端落在 `B` 之前，这一轮等于没判、`B` 一步推不动，缺口原样留着又拉起连接。第二个代价是白等最多 60 秒。依据：第 `s` 秒可记账当且仅当 `s + MINUTE_SETTLE_SEC <= now`，这对每一秒单独成立，与分钟边界无关 |
| `B` 与 `vital_ready_ranges` 全部改为秒级，不整分钟对齐（第 4 节、5.1） | 同上。逐分钟判定仍然按分钟做，但可判范围是 `[M, min(M+60, stableCeiling))`，不再被整分钟下界一笔勾销。相邻 ready 区间写入时按 `from_sec == 前一条 to_sec` 合并。整分钟对齐只保留在 30 天保留窗口起点一处 |
| 删除 `readCeiling`，读取的 `startSec` 也不对齐（5.3、8.1） | `readCeiling = floor(now/60)*60 + 60` 的理由是「让两分钟页对齐整分钟边界」，但这个理由不成立：`0x3A` 收的就是裸的 UTC 秒，任意时间戳都行；现有代码的历史游标本来就是设备返回的 `page.startSec`（任意秒），从来没有对齐过。对齐反而有害——它把读取窗口末端往回推，9.3 那种几十秒的连接空洞**对齐后窗口可能直接变空**。`minutes = 2` 是每页步长，不是窗口对齐要求 |
| `BROADCAST_RESUME_GRACE_SEC` 重新定性为「强制推进」而非「容差吸收」（9.2、9.4） | 容差的第二个条件是**最长连续缺失 < 9 秒**，而连接空洞是连续的，所以容差实际只覆盖 **≤ 8 秒**。宽限值取 60 秒时，它对 9~60 秒的空洞执行的是**强制推进**——把设备里真实存在的几十秒当作「确认无数据」永久放弃。这是有意的取舍，取大的方向是宁可多放弃几秒也不反复连接 |
| 四个待验证数值改为运行时可调（新增第 14 节） | `minuteSettleSec` / `broadcastResumeGraceSec` / `bridgeSec` / `urgentGapIntervalMs` 都只有真机数据能定，而「改一次代码、重装一次」的调参节奏不可接受。改为走 `tunables.ts`：默认值即代码常量，本地覆盖用 `.cool/utils/storage.ts` 持久化（这些是要连续观察几天的量，重启就丢会让调参无法进行），入口放在测试页新增的第 7 个弹窗，日志与输入框同屏（调参的循环就是「改值 → 看 `广播接续` 的 `决策` → 再改」）。**读取点必须是调用时读，不能模块加载时快照**——`sync` / `broadcast` / `gatt-scheduler` 都是长驻服务，常量在模块顶层读进变量就要重启才生效 |

## 16. 待真机验证的数值

**下表的「当前值」全部是代码里的默认值；运行时可覆盖，见第 14 节。**

| 常量 | 当前值 | 依据 | 风险 |
| --- | --- | --- | --- |
| `MINUTE_SETTLE_SEC` | 10 秒 | 大于广播节流节奏即可 | 若固件秒级数据/Flash 写入有延迟，`missing` 会集中在每分钟末尾几秒。**这是四个可调参数里唯一会造成数据错误（而非效率损失）的一个**，偏大则 `B` 落后 `now` 更多，偏小则可能把设备未稳定的秒当成「确认无数据」 |
| `BROADCAST_RESUME_GRACE_SEC` | 60 秒 | 划定「多大的连接空洞值得为它多读一次设备」。**不是覆盖容差**——容差（连续 9 秒）只覆盖 8 秒以内的空洞 | **偏小的代价是反复连接**（小空洞被推给设备补读，每条连接多跑一轮）——这正是要避免的形态，宁可取大。偏大则连接留下的真数据被有意放弃得更多（9~60 秒那一段是强制放弃的） |
| 加急缺口连接间隔 | 待定 | 8.4：需保证「一次加急连接的收益大于它自己造成的空洞」 | 取太小 → 广播质量差时频繁连接，恶性循环；取太大 → 加急失去意义。真机按实际丢包率定 |
| `HISTORY_GATT_READ_BRIDGE_SEC` | 120 秒 | 沿用老值 | 偏大则合并过多、单次链路变长 |

注意 `MINUTE_SETTLE_SEC` 同时承担两个职责（广播分类余量 + 页面记账余量），这也是它成为唯一需要谨慎对待的常量的原因。若真机发现两者所需余量差异很大，可以拆成两个——但**要先有数据**，不要凭猜。
