# BOOM 基准时间与分钟级上传重构方案

本文档描述对当前「持久历史补录」（原第 8 节）的重构方案。补数据的**读取方式**（从后往前、两分钟步长、`0x3A`/`0x3B`）不变，改变的是**缺口从哪来**、**什么时候上传**，以及**连接不再有时长上限**。

## 1. 为什么要改

老流程的缺口来自「有界调和」：先写粗意图任务（`recent` / `incremental` / `archive`），再用 `HistoryCoverageService.inspect()` 比对本地覆盖，把没有 `ppi_data` 的秒收敛成 `repairRanges`。它有两个固有代价：

- 缺口判定要遍历 `ppi_data.timestamp`，30 天的 `archive` 一次比对要读 86 万个时间戳，所以必须切成 6 小时的 `scan` 窗口分轮推进，引入了 `scan` / `verify` 两类「不代表确认缺数据」的中间态任务。
- 缺口只能靠「本地没有」推断。设备长期关机、没佩戴的时间段与真正丢包的时间段在本地看起来完全一样，只能靠读一遍设备来区分，因此调和窗口推进和真实缺口混在一条队列里。

新流程引入一个**基准时间 `baseline_sec`**，把「已经记账过的时间」和「待补的时间」彻底分开，不再需要对整条时间轴做覆盖比对。

## 2. 基准时间的定义

`baseline_sec`（下称 `B`）满足：

> **`[0, B)` 的每一秒都已经记账完毕**，不需要再补。

「记账完毕」的两种形式：

1. **合格（qualified）**：该段的数据完整度达标（第 3 节）。
2. **已确认（confirmed）**：设备已被读取过该时间段，并返回了完整声明范围的响应，确认没有更多数据（未佩戴 / 关机 / 该段设备确实没记）。

**`B` 停驻是预期行为。** 一段不合格时 `B` 卡在该段起点不动，直到这段被补上或被设备确认无数据，才继续前进。`B` 只前进，不后退。

**`B` 之后的时间分两类，都不需要额外的表**：已记账的落在 `vital_ready_ranges` 里，没记账的就是**缺口**——缺口由 `B` 和 `vital_ready_ranges` 直接相减得出，不存表。

一条新增的总原则：

> **广播是广播，判断是判断，补数据是补数据。连接只做自己的事，它留下的缺口等下一次连接补。**

连接期间广播是停的，每一次连接都会留下一小段缺秒。这段缺秒不特殊处理，它就是普通缺口，由下一次连接一起读掉（9.3）。这样三段逻辑各自独立：广播负责采集、判断负责推进 `B`、连接负责补缺口——没有跨模块的时序约束。

广播是每秒一帧的实时快照（`utc` + 当前秒的指标），**不携带历史秒**，所以连接期缺秒只能靠 `0x3A`/`0x3B` 读回来。它由下一次连接顺带补掉，成本极低：GATT 读取速度是实时的 82.8 倍，读 300 秒只要 3.6 秒（9.3）。

## 3. 合格判定

**判定不看分钟边界。** 判定单元是**整个未记账区间**——就是 `[B, stableCeiling)` 减掉 `vital_ready_ranges` 之后剩下的那几段。判的只有两件事，两件都与分钟无关：

| 条件 | 判据 | 常量 |
| --- | --- | --- |
| 没有连续缺 9 秒 | 每一段连续缺失都 `< 9` 秒 | `MINUTE_MAX_MISSING_RUN_SEC = 9` |
| 缺失总量不到 30% | `missing * 100 < 区段长度 * 30` | `MISSING_TOTAL_PERCENT = 30` |

第 `s` 秒可以判定，当且仅当 `s + MINUTE_SETTLE_SEC <= now`（5.3 的 `stableCeiling`）。

**为什么不去按分钟切。** 按分钟切会**在分钟边界上把一段连续缺失拆成两半**，两半各自都可能小于 9 秒，于是一段真实的 9 秒空洞被容差误吃。整分钟这个单位本身也不承载任何语义——设备记的、广播发的、`0x3A` 收的都是裸的 UTC 秒，一分钟只是人读日志时的习惯刻度。

**两条判据管的是两件事，必须分两遍算。**

1. **连续缺失**（逐段）：一段连续缺失达到 9 秒就是**真缺口**。空口空洞是连续的，所以这一条是真正起作用的约束，它把容差的实际覆盖范围压在 8 秒以内。真缺口把这一段切成若干**候选区**，缺口本身不属于任何候选区。
2. **缺失总量**（逐候选区）：它防的是「很多段各 8 秒、加起来占了一大半」这种稀疏情形——只看连续缺失是看不出来的（每段都过得了第一关，合计却是 44%）。不过关则整个候选区都不记账。

第 1 遍先切、第 2 遍再算总量，是因为总量是「这一片有多稀疏」的度量，**必须在一个不被真缺口打断的连续区域里算**。整段一刀切会让一处真缺口把它后面几十秒在场的数据一起作废——`B` 停在缺口前面，后面合格的秒照常记进 `vital_ready_ranges` 等它（5.6），所以那些秒没有理由跟着陪葬。

**第三关只作用于贴着右端的缺失段**：右端之外还没判到，它可能还更长，不能按当前长度放过。右端之外已确认时（这一段的右端是被已记账区间截断的，不是 `stableCeiling`），贴着右端的段才是完整的。不设这一关，一个横跨 `stableCeiling` 的 11 秒空洞会被拆成两段各 8 秒以内，被容差整段吃掉。

**这两条阈值是「要不要去设备读这一段」的触发器，不是最终裁决。** 判不合格 → 成为缺口 → 连设备读一次。设备的回答才是终局：

- 设备有这段数据 → 秒数据落进 `ppi_data`，该段合格，并入 `vital_ready_ranges`。
- 设备没有这段数据（该段全 `FF`）→ 该段**确认无数据**，同样并入 `vital_ready_ranges`。

所以**任何一次读取都会让缺口消解**，`B` 一定能继续前进。如果只有「取到数据」才算消解，设备确实没记录的那一段会永远不合格、`B` 永远卡死——这是必须避免的死循环。

## 4. 两张表

数据库整体重做，不兼容老库（老库遇到问题直接卸载重装）。删掉 `vital_history_tasks` / `vital_history_state`，换成：

```sql
-- 基准时间。只有一行。
CREATE TABLE IF NOT EXISTS vital_sync_state (
  id INTEGER PRIMARY KEY CHECK(id=1),
  baseline_sec INTEGER NOT NULL
);

-- 已记账的连续区间（左闭右开，秒级，不整分钟对齐）。含两类：
--   合格区间（本地数据完整度达标）
--   确认区间（设备已响应并确认该段没有更多数据）
CREATE TABLE IF NOT EXISTS vital_ready_ranges (
  from_sec INTEGER NOT NULL,
  to_sec INTEGER NOT NULL,
  PRIMARY KEY(from_sec, to_sec)
);
```

**区间是秒级的，`B` 也是秒级的，都不整分钟对齐**（理由见 5.1）——对齐会让 `B` 停驻时出现死区。

**没有第三张表。** 缺口不存——它恒等于 `[B, ready[0].fromSec)`（见 5.2）；设备确认无数据也不单独存——它并进 `vital_ready_ranges`。

也不再需要「已分类游标」：分类是幂等的纯本地计算（第 5 节），每次从 `B` 走一遍即可，走多快只取决于 `ppi_data` 的行数。

## 5. 基准时间如何前进

### 5.1 分类 `classify(nowSec)`

把 `[B, 分类右端)` 从「未分类」变成「已记账」或「缺口」。**分类右端 = 5.3 的 `stableCeiling(now)` = `now - MINUTE_SETTLE_SEC`**，即「最后一秒已等够余量」的时刻。

**分类右端不是整分钟边界。** 第 `s` 秒可以记账，当且仅当它的数据已经稳定，即 `s + MINUTE_SETTLE_SEC <= now`，也就是 `s <= now - MINUTE_SETTLE_SEC`。这个条件对每一秒单独成立，与分钟边界无关，所以右端就是 `now - MINUTE_SETTLE_SEC`，不需要也不应该向上取整到分钟。取整有两个害处：

1. **产生死区，`B` 推不动。** `now = 12:00:38`、`MINUTE_SETTLE_SEC = 10` 时，整分钟版本给出 `12:00:00`。若此刻 `B = 12:00:20`（连接刚结束回到广播），分类右端落在 `B` 之前 → **这一轮等于没判，`B` 一步推不动**。而 `[12:00:20, 12:00:28)` 是广播已恢复、数据已在本地、且已经等够余量的秒，本该正常判定。缺口因此原样留着，下一次检查又拉起一条连接——这正是第 9 节要消除的「反复连接」。
2. **白等最多 60 秒。** `now = 12:01:09` 时整分钟版本给出 `12:00:00`，即整个 `[12:00:00, 12:01:00)` 都已等够 9 秒以上却仍不能判，`B` 干等近一分钟。这是纯粹的延迟，没有任何稳定性上的收益。

**判定与秒级右端不冲突。** 判定单元是未记账区间（第 3 节），右端同样由 `stableCeiling` 给：

```
对每个未记账区间 P = [P.fromSec, P.toSec)：
  P.toSec <= stableCeiling(now)，所以区间里的秒都已经等够余量
  在 P 里求缺失段，按第 3 节的三关判
  贴着 P.toSec 的缺失段若超出 stableCeiling 就还没定论，这一轮不给结论
```

**`B` 因此可以停在任意秒上，不再只是整分钟。** `B` 的语义是「`[0, B)` 已记账完毕」，没有任何理由必须对齐分钟。

**分类产出的是秒级右端，写入 `vital_ready_ranges` 时也不做整分钟对齐。读取侧的 `startSec` 同样不需要对齐**——设备的 `0x3A` 收的就是裸的 UTC 秒，任意时间戳都行（8.1）。整分钟对齐唯一保留的地方是 30 天保留窗口的起点（5.5）。

步骤：

1. 先减去已有 `vital_ready_ranges`，得到本次真正要判定的**未记账区间**集合。已记账的部分直接跳过，不需要重判——分类因此是幂等的。
2. 一次查询取出这些区间范围内 `ppi_data` 的 timestamp。
3. 走区间算术求出缺失段，**逐个未记账区间调 `assessSegment()`**：
   - 合格 → 合并进 `vital_ready_ranges`（与上一条相邻就延长它）。
   - 不合格 → 不记任何东西。它自动成为缺口，由 5.2 与读取路径消费。

**没有单轮扫描上限。** 老流程的 6 小时 `HISTORY_RECONCILE_SCAN_SEC` 是为了限制「遍历 30 天 86 万个时间戳」，而现在：查询只覆盖未记账区间，App 关闭期间 `ppi_data` 为空（查询瞬间返回零行），区间算术在内存里做。所以 3 天的空白是一次零行查询 + 若干次区间算术，没有理由截断。

### 5.2 缺口 `listRepairGaps(nowSec)`

**缺口不需要枚举表，它是从 `B` 和 `vital_ready_ranges` 直接读出来的**：

```
缺口1 = [B,                ready[0].fromSec)
缺口2 = [ready[0].toSec,   ready[1].fromSec)
缺口3 = [ready[1].toSec,   ready[2].fromSec)
...
缺口N = [ready[N-1].toSec, 读取右端)
```

`vital_ready_ranges` 为空时，缺口就是 `[B, 读取右端)`。

**读取右端 = `stableCeiling(now)` = `now - MINUTE_SETTLE_SEC`。** `listRepairGaps()` **只返回 `stableCeiling` 之前的缺口**；`stableCeiling` 之后的秒故意不读——那时读得到但记不了账（5.4），读了也白读，还会让「补到没有缺口为止」这个终止条件永不成立（9.1）。

**缺口与 ready 区间都是秒级的，不对齐整分钟**，端点直接当 `startSec` 用（设备接受任意时间戳，8.1）。因此一条 ready 区间可能是半分钟的（例如 `[12:00:20, 12:00:28)`），缺口也可能只有几秒——减法在秒上是自洽的，不影响任何推导。

因为 `B` 只能推进到 `ready[0].toSec`，所以**任何时刻只有一个活跃缺口**：

> **缺口 ≡ `[B, ready[0].fromSec)`**（`ready_ranges` 为空时 ≡ `[B, 读取右端)`）

补完这个缺口、推进 `B`、消费掉 `ready[0]` 之后，原来的 `ready[1]` 变成新的 `ready[0]`，下一个缺口**自动**就是 `[B, ready[0].fromSec)`。不需要枚举、不需要排序、不需要存储。

**相邻 ready 区间要合并。** 秒级右端下，两次广播跨分钟判定可能产出 `[12:00:00, 12:00:28)` 与 `[12:00:28, 12:01:00)` 这样首尾相接的两条；写入时如果 `from_sec == 前一条的 to_sec` 就合并，避免行数虚增。

**几秒宽的小缺口不值得单独触发一次读取。** 它们由 8.2 的桥接合并进邻近的读取窗口；若整个缺口组都只有几秒宽（典型成因是连接留下的），会被容差直接吸收（连续缺失 < 9 秒），连缺口都不产生。

### 5.3 一个余量、一个边界

```
stableCeiling(nowSec) = nowSec - MINUTE_SETTLE_SEC   -- 记账右端，也是缺口右端
```

`MINUTE_SETTLE_SEC = 10` 秒。以 `now = 12:30:05` 为例：`stableCeiling = 12:29:55`。

`stableCeiling` 是**唯一**的边界，三处共用：

| 用途 | 说明 |
| --- | --- |
| 记账右端 | 允许被写进 `vital_ready_ranges` 的上界（5.4） |
| 缺口右端 | `listRepairGaps()` 的右端（5.2） |
| 分类右端 | `classify()` 的右端（5.1） |

**除此之外没有第二个边界。** 读取窗口直接取缺口端点和「设备返回的最晚秒」，设备对 `0x3A` 的起始时间没有任何对齐要求（8.1）。

**它的含义是「最后一秒已经等够余量、可以放心记账」**，所以是「`now` 往前 10 秒」，与分钟边界无关（5.1）。

**两条写入路径共用同一个余量。** 它们的余量本质是同一件事——都是「10 秒量级的传输/写入延迟」：

- 广播分类：最后几秒的广播包还在途中。
- 页面记账：最后几秒设备可能还没写好。

若真机测出固件写入延迟确实大于 10 秒，**只需调大这一个常量**，广播分类、页面记账、缺口右端三处一起调整，不会出现两处漂移。它同时是运行时可调的（第 14 节）。

### 5.4 记账规则

「把一段范围记为已记账」只有一个入口：

```
记账 [from, to)：
  to = min(to, stableCeiling(now))
  有效秒        → 数据
  FF / 缺行     → 设备确认「这里没有」
  超出 to 的部分 → 不记账，留在缺口里等它自然稳定（不重读、不确认）
```

`stableCeiling` 之前的范围已经稳定，`FF` 是确定的「设备没有」，可以永久记账。超出它的部分尚无定论，所以既不写 `vital_ready_ranges`、也不当作可读缺口（`listRepairGaps()` 同样封顶在这里），只是等时间走过去。`to` 是秒级的，不向上取整到分钟。

**`advanceBaseline()` 因此不需要任何 clamp**（5.5）：`vital_ready_ranges` 里的每一段右端都不超过 `stableCeiling`，`B` 的上界自动成立。这是把约束下沉到写入路径的好处——约束在数据写入那一刻就成立，而不是事后去拦 `B`。

### 5.5 推进 `advanceBaseline()`

纯表操作，**不查 `ppi_data`，也不做任何 clamp**：

```
若 B 早于 30 天保留窗口 → B 直接跳到保留起点（整分钟对齐），一次性放行
循环：
  B 落在 ready[0] 内（fromSec <= B < toSec）→ B 前进到 ready[0].toSec，消费 ready[0]
  否则               → 停
```

`B` 的上界由 5.4 的记账规则自动保证：写进 `vital_ready_ranges` 的每一段右端都不超过 `stableCeiling`。

**消费 `ready[0]` 要区分整条删除和拆条**：

- `ready[0].toSec <= B` → 整条删除（这一整段都已记账）。
- `ready[0].fromSec < B < ready[0].toSec` → **只改 `from_sec` 为 `B`，不删行**。例如 `B` 推进到 12:30:20 而 `ready[0] = [12:10, 13:00)`，`to_sec` 之后的 40 分钟还没被消费。

**`B` 落在 ready[0] 之前是正常停驻，不是错误。** ready 区间都是秒级的（5.1），`B` 可能停在任意秒上；`[B, ready[0].fromSec)` 就是当前那个唯一的活跃缺口（5.2）。

保留窗口那一步必须**直接跳到保留起点**，不能逐分钟放行：`B` 可能因设备长期连不上而停在几个月前，逐分钟是几万次带表查询的循环。跳到保留起点是一次操作，同时删除早于保留起点的 ready 区间——那些秒永远补不回来了，留着只会在弹窗和启动时被反复遍历。

调用时机：

1. **广播跨整分钟**（正常路径）。分类推进到 `stableCeiling(now)`，把本轮新稳定的秒并进 ready 区间，再推进 `B`。
2. **连接结束**：不需要特殊动作。连接期间停广播产生的缺秒按普通缺口处理，下一次连接补（9.3）。
3. **10 分钟自动检查**。兜底，处理广播长时间没来之后的情况。

### 5.6 为什么 ready 区间要单独存

- **`B` 之后「合格但被 `B` 卡住」的秒有了归属**，否则 `B` 一卡，那些秒既不在 `B` 里也没被打上任何标记。
- **缺口由减法直接得出**，不需要缺口表，也不需要排序——`ready` 区间天然有序。
- **`advanceBaseline()` 变成纯表操作**，不再查 `ppi_data`，更快也更好测。
- **连续区间自动合并**，行数是 O(不合格段数)，不是 O(时间)。`B` 卡一天的代价是 1 条 ready 区间，不是 1440 行。

正常运行时 ready 区间是**瞬态**的：建完立刻被 `advanceBaseline()` 消费掉。它只在 `B` 卡住时驻留——正好是它该起作用的时候。

## 6. App 没开 / 长时间没有广播

因为缺口是推导出来的，而分类永不停止，这个场景不需要任何特殊处理：

1. 重开后 `B` 停在关闭前的时刻，它到现在的全部时间都是「未记账」。
2. `classify()` 立刻把它们判完。App 关闭期间没有广播 → `ppi_data` 为空 → 整段不合格 → 整段是缺口。
3. `listRepairGaps()` 直接给出这段缺口，从缺口**末端起读**（8.1），不必等分类追平。
4. 读取后 `B` 推进。

**设备一跳就能确认掉「确实没数据」的整段。** 如果设备在这期间没被佩戴，查 `anchor=now` 向更早翻时首页的 `startSec` 会直接落在缺口起点之前——一次 `0x3A` 就把整段确认成已记账，不会翻几千页。只有设备**真有数据**时才逐页读，而那正是我们要读的。所以「App 关 3 天」的代价：没佩戴 → 一次往返；佩戴了 → 读 3 天的数据（本来就要读）。

## 7. 分钟级上传

上传策略整体替换掉老的「30 条 / 30 秒」批量触发。三个触发点，一个入口 `uploadData()`：

| 触发点 | 位置 | 职责 |
| --- | --- | --- |
| 广播跨整分钟（主） | `broadcast.ts` 的 `uploadCompletedMinuteIfCrossed` → `onMinuteCompleted` | 上传刚走完的那一分钟 |
| 60 秒定时兜底 | `startUploadTimer` | 消费 `uploaded=0` 积压 + 失败重试 |
| 历史补录落库后 | `readVitalRange` 的 finally → `scheduleUpload` | 异步排空，不阻塞 GATT 释放 |

- **触发点**：广播 `utc` 跨过整分钟时，上传刚走完的那一分钟。**秒级广播本身只落库，不驱动上传**——每秒一帧的实时流唯一能影响上传的地方就是跨过分钟边界那一次。
- **入口只有一个**：三个触发点都调 `uploadData()`，PPI 那侧只做「有待传记录 + 不在失败退避中就传」，**没有条数与间隔阈值**。节奏由触发点决定，不在入口再节流一次；失败后退避 `UPLOAD_FAILURE_BACKOFF_MS = 60 秒`，退避只作用于自动路径，手动上传不受影响。
- **判定与上传是两件事**：先上传该分钟的未上传秒，再做合格判定。**判定依据是本地的 `ppi_data`，不是上传结果**——基准时间描述的是「数据是否收齐」，上传是独立的可重试动作。上传失败时 `uploaded` 保持 0，由重试路径继续消费，不会因为弱网把已经收齐的分钟判成待补。
- 保留 `PPI_UPLOAD_MAX_RECORDS = 300` / `PPI_UPLOAD_MAX_BATCHES = 10` 作为**积压排空**的上限（历史补录落库的秒可能远超一分钟），但正常实时路径每个整分钟只有一批。
- 保留定时兜底，但降级为**重试与排空**：间隔 `UPLOAD_RETRY_INTERVAL_MS = 60 * 1000`，只为消费 `uploaded=0` 的积压和失败重试，不再作为主触发。

## 8. 补数据：一次一个缺口，补完推进再下一个

补录的基本循环：

```
读缺口 [B, ready[0].fromSec)  →  落库 / 确认  →  B 推进，消费 ready[0]  →  下一个缺口
```

因为 `ready[0]` 被消费后 `ready[1]` 变成新的 `ready[0]`，**下一个缺口自动浮现**，不需要重新枚举。所以「一直是 `B` 到第一条数据的开始时间是缺口」。

### 8.1 读取方向：缺口内从后往前

两方面不是一回事，不要混：

- **缺口顺序**：从 `B` 往前走——先补第一个缺口。
- **缺口内读取方向**：`anchor` 取缺口的**末端**，`direction = 0` 向更早翻页，翻到缺口起点。

这就是文档第 8 节标题「两分钟倒序读取」讲的 `0x3B` 方向。大缺口（App 关了 3 天）因此是从**最新端**开始读的，最新数据最先落库。

**`anchor` 取缺口末端的原始秒，不做任何对齐。** 设备的 `0x3A` 收的就是裸的 UTC 秒（[protocol.ts:296-312](.cool/store/device/protocol.ts#L296-L312)），**任意时间戳都行，设备没有「必须整分钟」的要求**。对齐是我们自己发明的约定，代价是丢掉最多 59 秒的可读窗口——对连接留下的几十秒缺口尤其明显（对齐后窗口可能直接变空）。现有代码的历史游标本来就是设备返回的 `page.startSec`（任意秒），从来没有对齐过，所以这里也不需要引入。

**读取窗口的右端**取「缺口末端」与「设备返回的最晚秒」的较大值，同样不向上取整。`minutes = 2` 是**每页步长**（翻页时向更早走 2 分钟），不是「窗口必须对齐到 2 分钟」——两者不是一回事。

### 8.2 桥接：把碎缺口并成一条链路

纯「一次只补一个缺口」在丢包场景下会碎片化。例如 12:05 和 12:07 两段不合格、12:06 合格，则 `ready[0] = [12:06,12:07)`，会拆成两个缺口、两条 `0x3A` 链路。丢包率高时（30% 丢包 → 约三成秒缺失）一小时能拆出几十条链路。

所以实际读窗口 = **第一个缺口，向前桥接跨过的短 ready 区间**，沿用文档的 `HISTORY_GATT_READ_BRIDGE_SEC = 120`：

```
读窗口 = [B, 末端)
末端 = 从 ready[0].fromSec 起，只要「下一个缺口的宽度」+「中间 ready 区间宽度」都在 120 秒内就继续向前合并
```

桥接跨过的秒本地已有，不重复入库。读完后 `B` 一并推过整个窗口。这等价于「相距 120 秒内的缺口合成一组」，但表述仍从 `B` 出发，仍然只有一个活跃缺口组 —— 不破坏「一次一个缺口」的模型。

### 8.3 读取链路与收尾

- **范围**：一次连接把 `listRepairGaps()` 的缺口**一次读完**（不循环，理由见下）。补不完的留给下一次连接。
- **连接没有时长上限**：需要补的缺口就一直补，补到完成再断开。原来「120 秒必须断开把通道还给广播」的约束不再需要——连接留下的缺口就是普通缺口，等下一次连接补（9.3）。
- **读取方式**：沿用整组一次 `0x3A`、之后连续 `0x3B`，每页先落库再续读。每页落库后：
  - 有效秒写入 `ppi_data`（`uploaded=0`）。
  - 按 5.4 的记账规则把该页可确认的范围并入 `vital_ready_ranges`——**只记到 `stableCeiling`；超出部分不记账**，等它自然稳定。
- **收尾**：
  - 设备返回段早于整个缺口（`page.startSec < 缺口.from_sec`，或 `startSec=0`）→ 该缺口设备无数据，整段按 5.4 记账。这是设备关机 / 未佩戴的正常路径，**不是失败**，继续读下一组。
  - 响应结构截断（秒数超出声明、残缺 6 字节记录）→ 视为链路错误，中止本轮。
  - 超时 / 发送失败 → 中止本轮。已提交的页面保留，剩余缺口留在原地，下一次连接重来。
- 补录落库后调用 `scheduleUpload()` 异步消费，不阻塞 GATT 释放。

**为什么是「一次读完」而不是循环补读。** 读到的东西越多耗时越长，而耗时就在制造新的尾巴。看起来应该循环把它也读掉，但算一下账就会发现不值得：

| | 第 1 轮（一次读完全部缺口） | 第 2 轮 | 第 3 轮 |
| --- | --- | --- | --- |
| 读的秒数 | `T` | `T/83` | `T/83²` |
| 耗时 | `T/83` | `T/83²` | `T/83³` |
| 剩余尾巴 | `T/83` | `T/83²` | `T/83³` |

（83 = GATT 读取速度，见 9.6。）

第 2 轮省下的真数据是 `T/83 - T/83² ≈ 0.988 × T/83`，代价是再占 `T/83²` 秒 GATT。而只要 `T ≤ 11 分钟`，`T/83 ≤ 8 秒`，**这个尾巴本来就被容差吸收、根本不算缺口**（第 3 节的连续缺失 < 9 秒）——所以第 2 轮省下的是 **0**，纯粹多占用 GATT。

所以是**一次读完，剩下没读的留给下一次连接**（9.3）。`T` 很大时（手动测试页长读、长时间事件回补）多跑一轮能省下 `T/83` 秒的真数据，但常态下不值得——那点秒数本来就会被容差吸收，而多跑一轮要多占 GATT。

**终止条件**：一次读完，`listRepairGaps()` 在 `stableCeiling` 之前的部分全部落库记账，所以下一轮（如果有）不会重复读到它们。9.1 的封顶保证读取不会去碰 `stableCeiling` 之后那些记不了账的秒。

**失败退避由连接间隔天然提供。** 缺口不落库，所以没有 `retry_at` / `attempts`。读取失败后缺口仍在，下一次连接至少 10 分钟后才来，自然重试。

补录完成后不需要额外的「核验」任务：`B` 自己会重新推进，合格的秒自动被吸收进基准时间。

### 8.4 广播缺秒：记录、合并，等下一次连接一起补

广播缺行只有一种成因：**那一秒的广播帧没收到**（空口丢包 / 系统漏扫）。设备不佩戴也会广播，那只是指标全 0，仍然会落一行（第 7 节）。所以缺行 ≠ 设备没记——**设备历史里大概率有这一秒，连一次就能补回真数据**。

即便如此，结论仍然是**不立刻连接**，把它交给 5.2 的缺口推导和 9.6 的自动检查：

- **代价不划算，而且代价几乎与缺口宽度无关。** 一次连接的开销固定在停扫描 / 直连 / 初始化握手 / 断开静默（350ms + 120ms）/ 重启扫描这几步上，是**数秒**量级；而补 1 分钟缺口只要 1 页、约 1.45 秒。为几秒的丢包付数秒的连接开销，并且这段时间广播是停的，收益是负的。
- **延迟没有用户可见的代价。** 实时展示走的是实时广播流，不是 `ppi_data` 补录；补一秒钟的早晚，只影响历史数据的补齐和上传时点，不影响用户看到的任何东西。
- **设备是历史的权威，晚补不丢数据。** 秒数据在设备 flash 里，缺口不落库也不会过期；5.5 的 30 天保留窗口是唯一的时间约束。
- **`B` 停驻本来就是预期行为**（第 2 节）。`B` 卡在失败的那一段，后面合格的秒堆在 `vital_ready_ranges` 里等它（5.6），行数是 O(失败段数)，不是 O(时间)。丢包率高时 8.2 的桥接会把 120 秒内的碎缺口并成一条链路，一次连接读完。

**缺口没有加急连接。** 早先设计过两类加急触发（广播静默后恢复、缺口宽度 ≥ 120 秒），**全部删除**：

| 曾经的触发 | 为什么删掉 |
| --- | --- |
| 广播静默后恢复 | 静默恢复本身就是「广播回来了」，此时最该做的是让广播把数据补上——`B` 会随分类自然推进，积压的部分等下一次自动检查。加急连接反而立刻把刚恢复的广播再掐掉 |
| 缺口宽度 ≥ 120 秒 | 判据再精细也改变不了根本的账：加急的收益是「早几分钟补上几秒丢包」，成本是「多一次连接 + 掐掉一段时间广播」，而用户看不到任何差别（实时展示走广播流）。拖久了会滚大这个理由不成立——8.2 的桥接让它一次连接读完，不会滚 |

**缺口就等着补。** 唯一的触发是 9.6 的 10 分钟自动检查（以及校时/事件这类本身就需要的连接顺带处理）。这样连接次数完全由「本来就必须连的事」决定，缺口不参与制造连接。

**连接次数减不掉，也不需要减。** 校时、事件读取、用户手动的设置类命令（0x31/0x35 等）都必须连接，这些次数由业务决定，跟缺口无关。所以缺口不参与制造连接——它不触发加急连接，只搭 10 分钟自动检查的顺风车。连接留下的那几秒缺口也走同一条路，等下一次检查顺带补掉（9.1）。

## 9. 连接生命周期

**这一节没有特殊机制。** 连接就做连接自己的事(校时 / 事件 / 补录),做完断开。它期间掐掉广播留下的缺秒,按普通缺口处理——**下一次连接来补**。

**连接不再设时长上限。** 一次 flush 需要读多久就读多久,补到完成再断开。

### 9.1 连接期间形成的缺口

连接掐掉一段广播,这段秒既不在 `B` 里、也不在 `vital_ready_ranges` 里,所以**它天然就是 `listRepairGaps()` 会返回的普通缺口**(9.2 说明了为什么不需要识别它)。断开恢复广播后:

1. 广播正常续上,新的秒照常落库、分类、推进 `B`。
2. 连接期那段缺秒留在缺口列表里。
3. **下一次连接**(10 分钟自动检查,或任何本来就要连的任务)把它一起读掉。

不需要 force-B、不需要读自己的空洞、不需要空洞识别、不需要接续判定。连接留下的缺口由下一次连接消化——这正是「缺口就等着补」。

### 9.2 连接空洞本来就是普通缺口

不存在「识别这是连接造成的空洞还是丢包造成的缺口」这个问题:两者在 `listRepairGaps()` 眼里**完全一样**,都是「既不在 `B` 里也不在 `ready_ranges` 里的秒」。

**这条认识删掉了整套「空洞识别」机制。** 早先设计的 `holeFrom`(停广播那一刻的整秒)、`tail`(连接留下的空洞宽度)、`BROADCAST_RESUME_GRACE_SEC`(宽限值)、`CONNECTION_LONG_THRESHOLD_MS`(连接时长判据)、广播接续判定、以及断开前的定向补读,都是我为「识别并特殊处理连接空洞」造的东西。

### 9.3 稳定状态:每次连接补上一次的,留下一次补

**每次连接都会留下一点缺口,由下一次连接补掉——这是被接受的设计,不是需要消除的问题。**

设连接的**固定开销**为 `O`(停扫描 / 直连 / 握手 / 断开静默 350ms+120ms / 重启扫描,与被读的数据量无关),本次要补的缺口为 `G`,GATT 读取速度 82.8 倍实时(1 页 2 分钟数据 = 1.45 秒)。

```
本次连接留下的空洞 = O + G/82.8,留给下一次连接
```

代入 `O = 5 秒`、`G = 300 秒`(补一条 5 分钟连接造成的积压):

| 第几次连接 | 要补 | 读取耗时 | 留下的空洞 |
| --- | --- | --- | --- |
| 1 | 300 秒 | 3.6 秒 | 8.6 秒 |
| 2 | 8.6 秒 | 0.1 秒 | **5.1 秒** |
| 3 | 5.1 秒 | 0.1 秒 | **5.1 秒** |

**稳定在一个固定的空洞上,不增长。** 迭代式 `G' = O + G/82.8` 收敛到 `O/(1-1/82.8) ≈ 1.012·O`,所以:

- 空洞**有界**,不会滚大——每次连接只补掉上一次留下的那一个,不会累积。
- 稳态就是**每 10 分钟连一次,每次补掉上一次的几秒缺口,再留下几秒**。

**这被明确接受。** 收益是设计极简:没有 force-B、没有空洞识别、没有接续判定、没有连接时长判据。代价是永远有几秒到十几秒的缺口在等下一次自动检查——而这几秒的真数据**设备里一直有**(那个时段用户在戴着设备,秒数据在 flash 里),等 10 分钟不会丢。

**一个可选优化,不做也不影响正确性**:如果 `O` 恰好落在 8 秒以内,那么第 2 次连接的空洞会被容差(最长连续缺失 < 9 秒)直接吸收、**连缺口都不产生**,于是不再需要第 3 次。那时稳态是「没有缺口」。这不是要达到的目标,只是顺带的好处——`O` 是多少由真机决定,不需要为它调任何东西。

### 9.4 `MINUTE_SETTLE_SEC` 与这件事无关

两个常量经常被混在一起,但它们毫不相关:

| 常量 | 作用 |
| --- | --- |
| `MINUTE_SETTLE_SEC = 10` 秒 | 等多久才**判定**（避开在途的广播包 / 未落的 Flash）。只决定「什么时候判」,不决定「判合格还是不合格」 |
| `MINUTE_MAX_MISSING_RUN_SEC = 9` 秒 | 最长连续缺失达到多少就**判不合格**。它才是「几秒的空洞可以被容差吸收」的来源。判定不按分钟切,所以它作用于未记账区间里的每一段连续缺失 |

所以调 `MINUTE_SETTLE_SEC` 只会让 `B` 落后更多或更少,对连接留下的空洞**没有任何影响**。

### 9.5 广播自然推进

连接留下的最后 10 秒(`stableCeiling` 之后)不属于任何缺口——它们尚未稳定、本轮不记账,由广播在走完余量时正常吸收(5.1)。连接结束时 `B` 与当前时间的差距就是这样来的,不是缺口的累积。

**广播在线时**:`B` 由分类推进到 `stableCeiling ≈ now - 10s`,每次分类都在追。
**广播离线时**(App 后台/关闭):`ppi_data` 不增长,缺口会累积,但此时没有广播要保护,连接可以一直补到 `stableCeiling`,补完断开放广播。

### 9.6 连接最小间隔

`MIN_CONNECT_INTERVAL_MS = 10 * 60 * 1000`。自动检查按这个间隔跑;一轮连接把积压补完,下一次连接至少 10 分钟后。这也顺带提供了缺口读取失败的天然退避(缺口不落库,没有 `retry_at`)。

**加急任务不受这个间隔限制**:校时、广播 `eventSeq` 变化触发的事件读取、用户手动的设置类命令(0x31/0x35 等)都立即连接——这些本来就是「必须连」的事。**缺口不在这里**:没有加急缺口(8.4),缺口只等这个 10 分钟的间隔。

**这个间隔同时是「缺口要等多久才被补」的上界**,包括连接自己留下的缺口。所以连接留下的缺秒最坏情况会等 10 分钟——这正是 9.3 那个收敛前提要成立的原因:如果 `O > 8 秒`,这个「等 10 分钟」就会变成常态而非例外。

放置位置:这段逻辑属于 `DeviceGattScheduler.flush()` 的收尾,紧挨现有的 `switchToBroadcastMode()`。**不需要在 `switchToConnectMode()` 里记录任何东西**(9.2)。

## 10. 读取日志

缺口不落库之后，日志成了唯一的观测手段，必须能回答「这次连接读了什么、补了多少、`B` 推到哪、还剩多少」。四层日志：

**连接层**——回答「这次连接值不值」

```text
[BOOM-HISTORY] 开始补录: B=..., 缺口组=..., 缺口秒=..., bridge秒=..., stableCeiling=..., 连接开始=...
[BOOM-HISTORY] 补录结束: B=...->..., 已补组=..., 失败组=..., 落库秒=..., 剩余缺口=..., 剩余秒=..., stableCeiling=..., 连接时长=...s, ok=...
```

`连接时长` 是判断「连接在做什么」的关键一列。**稳定运行时它应当就是连接的固定开销**（停扫描 / 握手 / 断开 / 重启扫描），因为那时没有积压、只补上一次留下的几秒（9.3）。它随时间持续增长说明缺口在积压。

`B=...->...` 是整轮的唯一结论。`剩余缺口` 与 `剩余秒` 直接来自 `listRepairGaps()` 的重算，是「还有多少活」的确切数字。`开始补录` 里的 `stableCeiling` 与 `B` 的差量就是「这次连接要补多少」，和 `补录结束` 的 `连接时长` 一起看能判断读取效率是否正常（82.8 倍实时）。

**缺口组层**——回答「这一组读到哪、为什么停、记账推进了没有」

```text
[BOOM-HISTORY] 缺口组读取开始: window=...~..., 缺口秒=..., bridge秒=..., anchor=..., minutes=2, direction=0
[BOOM-HISTORY] 缺口组读取结束: window=...~..., status=..., pages=..., 秒记录=..., 有效秒=..., 全FF秒=..., 落库=..., 已记账=...s, elapsed=...s
[BOOM-HISTORY] 缺口组读取失败: window=...~..., status=..., pages=..., message=...
[BOOM-HISTORY] 缺口组结束: n/m, window=...~..., 缺口秒=..., bridge秒=..., status=..., pages=..., 落库=..., B=...->..., 本组推进=...s
```

`缺口秒` 与 `bridge秒` 分开打印：前者是真正要补的秒，后者是合并相邻缺口时跨过的已有秒。两者一起看才知道合并省了多少次往返。

`本组推进` 是核对「记账是否按预期推进」的**直接证据**：它是这一组的读取前后 `B` 的差量。`落库` 有值而 `本组推进=0` 说明读到的秒没有转成记账（被 `stableCeiling` 封顶，或那一页的记账被跳过）——这两件事必须分开看，`落库` 正常不代表 `B` 动了。

**页层**——默认不打印，只在落库与确认时打印

```text
[BOOM-HISTORY] 页落库: page=..., 新增秒=..., 记账=...~...
[BOOM-HISTORY] 设备无数据确认: window=...~..., confirmed秒=...
[BOOM-HISTORY] 设备返回段早于目标窗口，按无数据收尾: page=..., window=..., confirmed秒=...
```

页层是「补录卡在某一段」的唯一线索，但它不逐页打印——逐页会把诊断缓冲区冲掉。所以页级的诊断计数**累计后合并进 `缺口组读取结束` 那一行**：`全FF秒` 与 `秒记录` 相等说明设备确实没记这段（正常路径，不是故障）；`有效秒` 远小于 `秒记录` 说明解码有问题。结构非法的页（`n` 越界、`rmssdSdnn` 长度不符）和「未向更早推进」会以 `页面处理失败` 抛出并终止本轮，在 `缺口组读取失败` 的 `message` 里可见。

所有日志走 `.cool/service/logger.ts` 进诊断日志，不 `throw`、不只用 `console`。

## 13. 日志检查清单

```text
[BOOM-BASE] 分类完成: 未记账=...s, 新记账=...s, 新缺口=...s, 不合格段=..., 分类右端=..., B=..., 用时=...ms
[BOOM-BASE] 段不合格: 区间=...~..., 长度=...s, 缺失=...s, 最长连续缺失=...s, 阻塞段数=..., 阻塞秒=...s, 阈值=缺失<30%, 连续<9
[BOOM-BASE] 基准推进: B=...->..., 消费ready区间=..., 原因=ready/expired, stableCeiling=..., 落后=...s
[BOOM-BASE] 基准停驻: B=..., 阻塞起点=..., 缺口组=..., 缺口秒=...
[BOOM-BASE] 刻度: now=..., stableCeiling=..., B=...
[BOOM-BASE] 分钟边界: minute=..., 未记账=...s, 新记账=...s, 不合格段=..., B=..., stableCeiling=...
[BOOM-UPLOAD] 分钟上传: minute=..., ok=...
```

- `分类完成`：每轮判了多少秒、产出多少缺口。**分类永不停止是设计前提**，这一行长期不动说明 `ppi_data` 查询或区间算术出了问题。`分类右端` 就是 `stableCeiling`，便于核对它是否等于 `now - minuteSettleSec`。
- `段不合格`：哪一段因为什么判失败。`区间` 是这一整段未记账区间（右端可能被已记账区间截断、也可能就是 `stableCeiling`），`缺失` 与 `最长连续缺失` 直接对应第 3 节的两条判据，`阻塞段数`/`阻塞秒` 是真正卡住的连续缺失（真缺口）有几个、一共多少秒，`阈值` 把判定线一并打出来，不用回翻代码。**贴着 `stableCeiling` 的失败不打这行**——那只是还没等到数据、下一轮会重判，打出来会把日志冲满。
- `基准推进` / `基准停驻`：`B` 为什么动或不动，后面还积压多少缺口。**`落后`（= `stableCeiling - B`）是排查「`B` 卡住不动」的第一现场**——两者都是秒级的、不整分钟对齐，所以正常情况下它贴着 0（几秒的落库延迟）。明显大于 0 说明前面有真缺口；`基准推进` 只在真动了的时候打印，所以「日志里一直看不到它」本身就是停驻的信号，此时去看 `基准停驻` 的 `缺口组` 与 `段不合格`。
- `刻度`：三个时间值一起打印，每轮自动检查一次。
- 连接层的 `开始补录` / `补录结束` 是「这次连接值不值」的结论，见第 10 节。**连接的稳定形态是「每 10 分钟一次，每次补掉上一次留下的几秒」**（9.3），所以 `[BOOM-SCHED] 开始执行队列` 的间隔稳定在 `HISTORY_AUTO_CHECK_INTERVAL_MS` 附近、且 `补录结束` 的 `连接时长` 稳定在一个小值上，就是健康状态——那个小值就是连接的固定开销。如果 `连接时长` 随时间**持续增长**，说明连接在补的缺口比它自己留下的更大（有外部缺口积压），去看 `基准停驻` 的 `缺口组`。

连接检查点与四层补录日志见第 9、10 节。

## 14. 运行时可调参数

这套设计里有两个数值只有真机数据才能定，而反复改代码重装才能调一次是不可接受的。所以它们**不写死在常量里**，走运行时配置：

```ts
// .cool/bluetooth/history/tunables.ts —— 新增
// 默认值 = 代码里的常量；有本地覆盖就用覆盖值；没有就返回默认值。
// 所有读取点都走这里，不允许别处直接引用默认常量。
export type HistoryTunables = {
	minuteSettleSec: number;  // 默认 10
	bridgeSec: number;        // 默认 120
};

export function getHistoryTunables(): HistoryTunables;
export function setHistoryTunable(key: keyof HistoryTunables, value: number): void;
export function resetHistoryTunables(): void;
```

**持久化用 `.cool/utils/storage.ts` 的 `storage.set(key, value, 0)`**，key 前缀 `boom_history_tune_`。**必须持久化**：这些是被长期观测的量，App 重启就丢会让「调一次、观察几天」变得不可能。`resetHistoryTunables()` 清掉全部覆盖、回落到默认值。

**读取点必须是调用时读，不能模块加载时快照。** 这些是长驻服务（`sync` / `broadcast` / `gatt-scheduler`），常量一旦在模块顶层读进变量，改了要重启 App 才生效，那就失去了可调的意义。每处用到的地方调用 `getHistoryTunables().xxx`。

**没有界面入口。** 早先设计过一个测试页弹窗（`HistoryTunePopup`：数值输入 + 生效值 + 「默认/已覆盖」标记 + 重置 + 当前日志），**已删除**——两个参数在真机跑过之后都没再动过，弹窗的维护成本（一个完整的读写/草稿/校验 UI）换不来实际收益。`tunables.ts` 的覆盖机制保留：默认值即代码常量，要临时改一个值仍是 `setHistoryTunable()` 一行，改完立刻生效。

**覆盖时要打日志**，否则「为什么行为和文档不一致」会很难查：

```text
[BOOM-TUNE] 参数覆盖: key=..., 默认=..., 生效=...
[BOOM-TUNE] 参数已重置: key=...
```

### 每个参数调错了会怎样

| 参数 | 默认 | 调小的后果 | 调大的后果 |
| --- | --- | --- | --- |
| `minuteSettleSec` | 10 秒 | 把设备还没写完的秒当成「确认无数据」，记错 | `B` 落后 `now` 更多，但更安全 |
| `bridgeSec` | 120 秒 | 碎缺口合并得少，读取链路变多 | 单次链路变长，一次连接占 GATT 更久 |

`MINUTE_SETTLE_SEC` 是两个里唯一会造成**数据错误**（而非效率损失）的，所以它的默认值改动要格外谨慎。

## 15. 变更记录

方案在讨论中经历了几次结构性调整。这里只记**决定与理由**，推导过程见正文对应章节。

### 2026-09-15 定稿

| 决定 | 理由 |
| --- | --- |
| 删除 `ACCOUNT_MARGIN_SEC = 120`，两条写入路径统一用 `MINUTE_SETTLE_SEC = 10`（5.3） | 那个 120 秒是从老流程 `historyStableBefore` 直接搬来的**未经验证的猜测**（老文档自己写着「尚无真机时延数据支撑」）。保留它只有一个后果：`B` 长期落后当前时间 2 分钟，而「每次连接都把基准推到尽可能新」正是这套设计的核心目标。两条路径的余量本质是同一件事，没有理由用两个值 |
| 读取范围封顶在 `stableCeiling`（9.1） | 原设计的 `listRepairGaps()` 读到最后 `now`，但记账受余量限制，最后的秒读得到却记不了账 → 缺口永不排空 → 死循环。根因是把「最后的秒还没稳定、不能确认 `FF`」和「这段是待读缺口」混成了一件事 |
| 4 张表减到 2 张：删除「待补窗口表」与「设备确认表」（第 4 节） | 缺口由 `B` 与 `vital_ready_ranges` 直接推导，不落库；设备确认无数据并进 `vital_ready_ranges`。代价是读取失败没有持久化的 `retry_at` / `attempts`，改由「连接最小间隔 10 分钟」天然提供退避 |
| 缺口推导改为「一次一个活跃缺口」（5.2） | `B` 只能推进到 `ready[0].toSec`，所以任何时刻只有 `[B, ready[0].fromSec)` 一个活跃缺口；补完推进后 `ready[1]` 顶上来，下一个自动浮现。不需要枚举、排序或存储 |
| 删除「已分类游标 `C`」 | 引入 `C` 是为了修「`B` 卡住时每轮重扫同一段」的真 bug。换成「分类幂等 + 无单轮上限」后不再必要——分类每次从 `B` 走一遍，已记账区间直接跳过，多走的成本只是内存算术 |
| 删除连接时长上限 `GATT_FLUSH_BUDGET_MS`（120 秒）与 `listBudgetedTasks()`（8.3） | 原上限的理由是「补录期间广播是停的，上限必须有界」。取消后长连接会留下长空洞，靠第 9 节收回：补 `T` 秒空洞要 `T/83` 秒（约 83 倍实时），新留下的 `T/83` 秒读回又要 `T/83²` 秒，几何级数求和约 `1.012T`，额外开销约 1.2%，不发散 |
| 删除 `scan` / `verify` 两类中间态任务与 6 小时有界调和 | 老流程切 6 小时是为了限制「遍历 30 天 86 万个时间戳」，新分类只查未记账区间，该理由不成立 |
| `advanceBaseline()` 去掉统一 clamp（5.4、5.5） | 早先用 `settledTo(nowSec)` 把 `B` 拦在「最后一个已过余量的整分钟」，那是**错误的位置**：未稳定的范围一旦写进 `vital_ready_ranges`，数据就已经错了，事后拦只是延后暴露。约束必须下沉到写入那一刻，`B` 的上界才自动成立 |

**未变的部分**：分钟合格判定的两个阈值（缺失 < 1/3、无连续缺 9 秒）、分钟级上传、缺口内从后往前读、桥接 `HISTORY_GATT_READ_BRIDGE_SEC = 120`、连接最小间隔 10 分钟、30 天保留窗口——这些从讨论开始就没有改动。

> 其中「分钟合格判定的两个阈值」后来变了：判定不再按分钟切，容差从 1/3 改为 30%，见 2026-09-17 修订（四）。

### 2026-09-16 修订：广播接续判定，切断「连接 → 缺秒 → 连接」的循环

| 决定 | 理由 |
| --- | --- |
| 新增 9.4 广播接续判定 | 连接一定会留下缺秒，而连接又只由「有缺口」触发——不在同一轮消化就会自己咬住自己，表现是反复连接。消化手段是广播：恢复后第一帧 `T0` 到达时，若 `T0 - B <= BROADCAST_RESUME_GRACE_SEC` 就整段按「确认无数据」记账并推进 `B` |
| 9.3 从「无条件补读」改为「仅大空洞补读」 | 判据改为空洞宽度 `tail > BROADCAST_RESUME_GRACE_SEC`，不是连接时长——留不留缺口取决于空洞形状。小空洞不读，因为 9.4 能免费得到同样的 `B` 落点，多读一轮只是多占几秒 GATT 又制造新空洞 |
| 新增 8.4：广播缺秒不立即连接 | 缺行只可能来自空口丢包（不佩戴也会广播，指标全 0 而已），设备历史里大概率有真数据。但连接开销固定为数秒，补 1 分钟缺口只要 1.45 秒，收益为负；实时展示走广播流不受影响；`B` 停驻本就是预期行为 |
| 加急连接只保留两类触发 | **广播静默后恢复**（`markBroadcastRecoveryOk()`，积压已确定存在），以及**缺口宽度 ≥ `HISTORY_GATT_READ_BRIDGE_SEC` 且广播当前在线**。「广播在线」这个前提不能省：广播离线期加急连接会边补边掐广播，退化成恶性循环。明确排除「缺口总秒数」作为触发——它无法区分「空口丢包」与「设备没记」 |

### 2026-09-16 修订（二）：`stableCeiling` 去掉整分钟对齐，`B` 与读取全部改为秒级

| 决定 | 理由 |
| --- | --- |
| `stableCeiling` 从 `floor((now - MINUTE_SETTLE_SEC)/60)*60` 改为 `now - MINUTE_SETTLE_SEC`（5.3） | 取整分钟会产生死区，直接破坏 9.4 的接续判定：`now = 12:00:38` 时整分钟版本给出 `12:00:00`，若 `B = 12:00:20` 则分类右端落在 `B` 之前，这一轮等于没判、`B` 一步推不动，缺口原样留着又拉起连接。第二个代价是白等最多 60 秒。依据：第 `s` 秒可记账当且仅当 `s + MINUTE_SETTLE_SEC <= now`，这对每一秒单独成立，与分钟边界无关 |
| `B` 与 `vital_ready_ranges` 全部改为秒级，不整分钟对齐（第 4 节、5.1） | 同上。逐分钟判定仍然按分钟做，但可判范围是 `[M, min(M+60, stableCeiling))`，不再被整分钟下界一笔勾销。相邻 ready 区间写入时按 `from_sec == 前一条 to_sec` 合并。整分钟对齐只保留在 30 天保留窗口起点一处 |
| 删除 `readCeiling`，读取的 `startSec` 也不对齐（5.3、8.1） | `readCeiling = floor(now/60)*60 + 60` 的理由是「让两分钟页对齐整分钟边界」，但这个理由不成立：`0x3A` 收的就是裸的 UTC 秒，任意时间戳都行；现有代码的历史游标本来就是设备返回的 `page.startSec`（任意秒），从来没有对齐过。对齐反而有害——它把读取窗口末端往回推，9.3 那种几十秒的连接空洞**对齐后窗口可能直接变空**。`minutes = 2` 是每页步长，不是窗口对齐要求 |
| `BROADCAST_RESUME_GRACE_SEC` 重新定性为「强制推进」而非「容差吸收」（9.2、9.4） | 容差的第二个条件是**最长连续缺失 < 9 秒**，而连接空洞是连续的，所以容差实际只覆盖 **≤ 8 秒**。宽限值取 60 秒时，它对 9~60 秒的空洞执行的是**强制推进**——把设备里真实存在的几十秒当作「确认无数据」永久放弃。这是有意的取舍，取大的方向是宁可多放弃几秒也不反复连接 |
| 四个待验证数值改为运行时可调（新增第 14 节） | `minuteSettleSec` / `broadcastResumeGraceSec` / `bridgeSec` / `urgentGapIntervalMs` 都只有真机数据能定，而「改一次代码、重装一次」的调参节奏不可接受。改为走 `tunables.ts`：默认值即代码常量，本地覆盖用 `.cool/utils/storage.ts` 持久化（这些是要连续观察几天的量，重启就丢会让调参无法进行），入口放在测试页新增的一个弹窗，日志与输入框同屏（调参的循环就是「改值 → 看日志 → 再改」）。**读取点必须是调用时读，不能模块加载时快照**——`sync` / `broadcast` / `gatt-scheduler` 都是长驻服务，常量在模块顶层读进变量就要重启才生效 |

### 2026-09-16 修订（三）：删掉全部特殊机制，连接只做自己的事

起因是三个反问，以及一句明确的要求:**「每次连接就做自己的事情,反正产生的缺口,下一次连接的时候可以补」**。

这一轮把第 9 节从「一套围绕连接空洞的机制」削成「什么都不做」。

| 决定 | 理由 |
| --- | --- |
| **新增 9.2:连接空洞本来就是「正常缺口」** | 它既不在 `B` 里、也不在 `vital_ready_ranges` 里,所以天然就是 `listRepairGaps()` 返回的缺口之一。这一条认识删掉了 `holeFrom` / `tail` / `BROADCAST_RESUME_GRACE_SEC` / `CONNECTION_LONG_THRESHOLD_MS` 四个量,以及围绕它们的全部长短分支 |
| **删除 force-B 与断开前的定向补读** | 它们是为「连接不在下一轮留缺口」造的。而用户明确接受连接留下缺口、下次连接补,所以这个目标本身取消了。第 9 节因此不再有任何特殊动作 |
| **删除 9.4 广播接续判定** | 同上——它是为「在广播路径上就地消化小空洞」造的 |
| **删除 8.4 的两类加急缺口连接** | 加急的收益是「早几分钟补上几秒丢包」,成本是「多一次连接 + 掐掉一段时间广播」,而用户看不到差别(实时展示走广播流)。缺口只搭 10 分钟自动检查的顺风车 |
| **9.3 改为「稳定状态」的说明,不再是「收敛性要求」** | 早先要求「连接留下的空洞必须在同一轮消化」,并论证它需要连接固定开销 `O ≤ 8 秒`。现在这个要求取消了:`G' = O + G/82.8` 收敛到 `≈1.012·O`,所以**空洞稳定有界、不滚大**,稳态就是「每 10 分钟连一次、每次补掉上一次留下的几秒」。这是被接受的设计,不是待解决的问题 |
| **明确三段逻辑独立** | 广播是广播(采集)、判断是判断(推进 `B`)、补数据是补数据(连接补缺口)。没有跨模块的时序约束——不需要「判定必须在缺口推导之前发生」,也不需要 `connection.ts` 记录任何东西 |
| **明确复杂度的价值不在「减少连接次数」** | 校时 / 事件 / 手动设置命令都必须连接,次数由业务决定,减不掉。缺口也不参与制造连接(无加急、不触发)。所以整套设计里没有「为减少连接而存在」的部分 |
| **第 14 节可调参数从四个减到两个** | `broadcastResumeGraceSec` 与 `urgentGapIntervalMs` 随各自的机制一起删除,只剩 `minuteSettleSec` 与 `bridgeSec` |

**这一轮的净效果**:第 9 节从 7 个小节、含 4 个常量与 2 个分支,变成「连接就是连接,缺口下次补」。删除 2 个常量、1 个运行时参数、2 类加急触发、1 个广播路径上的判定、1 个断开前的读取。**代价是永远有几秒到十几秒的缺口在等下一次自动检查**——而那几秒真数据设备里一直有,等 10 分钟不会丢。

**唯一仍然成立的量化认识**(写在 9.3,但不是要求):如果连接的固定开销恰好在 8 秒以内,第 2 次连接留下的空洞会被容差(最长连续缺失 < 9 秒)直接吸收、连缺口都不产生,于是稳态更进一步变成「没有缺口」。这是顺带的好处,不需要为它调任何东西。

### 2026-09-17 修订（四）：判定不再按分钟切,容差改为 30%

起因是一句要求:**「判断数据合不合格,不是严格按照 1 分钟来的,只判断传进来的数据有没有连续缺秒和一共缺了多少数据（不要搞 1/3,搞 30% 吧）」**。

第 3 节因此从「逐分钟的两条门槛」变成「逐未记账区间的两条门槛」:

| 决定 | 理由 |
| --- | --- |
| **删掉「分钟」这个判定单位**（第 3 节） | 判据本来就只有「连续缺了多少」和「一共缺了多少」两条,两条都与分钟边界无关。按分钟切还有实害:**边界会把一段连续缺失拆成两半**,两半各自都可能 < 9 秒,于是一段真实的 9 秒空洞被容差误吃。设备记的、广播发的、`0x3A` 收的都是裸的 UTC 秒,一分钟不承载任何语义 |
| **容差从 `missing * 3 < 60` 改为 `missing * 100 < 区间长度 * 30`** | 老式子里的 `60` 是分钟长度,不按分钟切之后就没有意义了;而且固定窗口对长区间过紧、对短区间过松。改成按区间长度等比缩放,`MISSING_TOTAL_PERCENT = 30` 才是真正的比例阈值 |
| **两条判据分两遍算**（`assessSegment()`） | 连续缺失先切、缺失总量后算,顺序不能反。总量是「这一片有多稀疏」的度量,**必须在一个不被真缺口打断的连续区域里算**——否则一处真缺口会把它后面几十秒在场的数据一起作废,而 `B` 停在缺口前面、后面合格的秒本该照常记账等它（5.6） |
| **「贴着右端未判完」从分钟截断改为区间右端** | 原来是「可判范围 `[M, min(M+60, stableCeiling))`」,现在是「未记账区间贴着 `stableCeiling` 的那一段不给结论」。作用不变:横跨 `stableCeiling` 的空洞不能被当前长度放过 |
| 删除 `minuteStartsIn()` / `MinuteAssessment` / `unqualifiedMinutes` | 判定单位没了,这些随之下线。`MINUTE_MAX_MISSING = 20` 也是死代码（声明了从未被读） |
| 日志 `分钟不合格` → `段不合格`（第 13 节） | 打的是未记账区间,不是分钟。字段同步改为 `区间` / `长度` / `阻塞段数` / `阻塞秒` |

**未变的部分**:一分钟这个刻度仍然留在它该在的地方——**分钟级上传**（第 7 节）按广播的整分钟边界触发,与合格判定无关。判定与上传本来就是两件事（第 7 节）。

### 2026-09-17 修订（五）：删掉补录参数弹窗

| 决定 | 理由 |
| --- | --- |
| **删除 `HistoryTunePopup.uvue`**（第 14 节） | 两个参数在真机跑过之后都没再动过,弹窗的维护成本（一个完整的读写/草稿/校验 UI,313 行）换不来实际收益。测试页入口随之从 7 个减到 6 个,`types.ts` 里的 `HistoryTunePopupProps` / `HistoryTuneItem` 一并删除 |
| **保留 `tunables.ts` 的覆盖机制** | 删的是界面,不是能力:默认值仍是代码常量,临时改一个值仍是 `setHistoryTunable()` 一行,改完立刻生效。第 14 节记录的机制没有变,只是不再有界面入口 |

### 2026-09-17 修订（六）：删掉「30 条 / 30 秒」闸门，上传入口收敛为一处

起因是对照真机日志核了一遍上传节奏，发现第 7 节与 §12 删除清单**写的和跑的不是一回事**：「30 条 / 30 秒」从未被删除，而且是它在驱动上传。

| 决定 | 理由 |
| --- | --- |
| **删除 `PPI_UPLOAD_BATCH_SIZE = 30` 与 `PPI_UPLOAD_MIN_INTERVAL_MS`**（第 7 节） | `count < 30 && elapsed < 30000` 让「攒够 30 条」和「距上次 30 秒」**各自单独放行**，实测每 30 秒一批。上传节奏应该由触发点决定，不该在入口再节流一次 |
| **整分钟触发原本被架空** | `onMinuteCompleted()` 走的是 `uploadData()` → 同一道闸门；分钟边界那一刻 `count < 30` 且 `elapsed < 30000` 两条都为真，直接 `return false`。所谓「主触发是整分钟」实际一次都没生效 |
| **`broadcast.ts` 删掉逐秒的 `requestPpiUpload()`** | 它在每条广播上都调，秒级实时流才是真正的驱动源，与「秒级的实时流不再驱动上传」正好相反。秒级广播改为只落库，上传只在跨整分钟那一次发生 |
| **入口收敛为 `uploadData()` 一个** | 五个入口（`requestPpiUpload` / `uploadData` / `scheduleUpload` / `startUploadTimer` / `onMinuteCompleted`）各带一套隐式节流，散落难查。现在三个触发点都调同一个入口，`requestPpiUpload()` 降为私有的 `uploadPpiIfPending()`，只剩「有待传记录 + 不在退避中就传」 |
| **退避值 30 秒 → `UPLOAD_FAILURE_BACKOFF_MS = 60 秒`** | 流程文档原本就写着「自动上传至少等待 60 秒再重试」，代码是 30 秒——又一处文档与代码不一致，一并对齐。退避只加在自动路径，`uploadPpiData()` 保持无节流的 worker 语义，测试页手动上传不受影响 |

**这一版之后**，第 7 节与 §12 的「『30 条 / 30 秒』上传触发」才是事实。真机验证形态：`[BOOM-UPLOAD] 分钟上传: minute=...` 每 60 秒一条，紧随其后 `上传PPI数据: batch=1, count≈60`。

## 16. 待真机验证的数值

**下表的「当前值」全部是代码里的默认值；`minuteSettleSec` 与 `bridgeSec` 运行时可覆盖，见第 14 节。**

| 常量 | 当前值 | 依据 | 风险 |
| --- | --- | --- | --- |
| `MINUTE_SETTLE_SEC` | 10 秒 | 大于广播节流节奏即可 | 若固件秒级数据/Flash 写入有延迟，`missing` 会集中在每分钟末尾几秒。**这是唯一会造成数据错误（而非效率损失）的参数**，偏大则 `B` 落后 `now` 更多，偏小则可能把设备未稳定的秒当成「确认无数据」 |
| `HISTORY_GATT_READ_BRIDGE_SEC` | 120 秒 | 沿用老值 | 偏大则合并过多、单次链路变长 |
| `MIN_CONNECT_INTERVAL_MS` | 10 分钟 | 沿用老值（老流程的 `HISTORY_AUTO_CHECK_INTERVAL_MS`） | 偏大则缺口补得晚；偏小则连接频繁，广播停摆时间上升 |

**不再需要真机标定的量**（早先设计有，已删除）：

| 曾经要调 | 为什么不需要了 |
| --- | --- |
| `BROADCAST_RESUME_GRACE_SEC` | 9.2 证明连接空洞本就是普通缺口，读取天然处理它，不需要「多大的空洞值得读」这个判据 |
| `urgentGapIntervalMs` | 8.4 删掉了加急缺口连接，缺口只等 `MIN_CONNECT_INTERVAL_MS` |
| `CONNECTION_LONG_THRESHOLD_MS` | 同上，不需要按连接时长做任何分支 |

**验证方法**：稳定运行后看 `[BOOM-HISTORY] 补录结束` 的 `连接时长` 列——它应当稳定在一个**小值**上（那个值就是连接的固定开销：停扫描 / 握手 / 断开 / 重启扫描），因为那时连接只补上一次留下的几秒（9.3）。**它随时间持续增长**说明有外部缺口在积压，去看 `基准停驻` 的 `缺口组`。**它固定在一个偏大的值（十几秒以上）**说明固定开销本身就高，空洞仍然稳定有界、不会滚大，但每次连接掐掉的广播更多，可以压缩停扫描 / 断开静默 / 重启扫描的等待。

注意 `MINUTE_SETTLE_SEC` 同时承担两个职责（广播分类余量 + 页面记账余量），这也是它成为唯一需要谨慎对待的常量的原因。若真机发现两者所需余量差异很大，可以拆成两个——但**要先有数据**，不要凭猜。
