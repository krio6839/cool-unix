# BOOM 蓝牙运行流程说明

本文档说明当前 App 对 BOOM 新设备的蓝牙运行策略，方便对照日志排查。

## 1. 总体原则

- 已绑定设备默认使用广播模式，不主动保持 GATT 连接。
- 0x50 广播是实时展示和实时 PPI 入库的主要来源。
- GATT 只作为任务执行通道，不主动长连；任务完成后断开并恢复广播扫描。
- 自动 GATT 业务统一进入 `DeviceGattScheduler` 队列，批量连接执行，避免事件、历史、校时等命令互相掺杂。
- 加急任务会立即触发队列执行；普通历史补缺由启动后和 10 分钟检查触发。
- 事件读取有两类来源：广播 `eventSeq` 变化入队、自动同步每 30 分钟兜底入队。
- 连接初始化只准备 services / characteristics / notify，不自动读固件版本，不自动读 0x50。
- 历史补录是否值得连接只由两份本地事实决定：`ppi_data` 有没有这一秒、设备是否已经确认读过这一秒。`ppi_data.timestamp` 是本地数据的唯一事实来源，`hr/spo2/ppi` 是否为零不影响“本地已有”的判断。已记账区间（合格或设备确认无数据）落在 `vital_ready_ranges`，待补的秒由基准时间 `baseline_sec` 与它相减直接得出，缺口不存表。
- 本地 PPI 原始数据只保留最近 30 天；早于保留窗口的时间不扫描、不展示为待补，也不会创建 GATT 任务。
- 连接不再设时长上限：一次 flush 需要读多久就读多久，补到本轮冻结计划结束再断开。连接期间新产生的缺秒不扩进本轮计划，按普通缺口由下一次连接处理（第 7 节）。

## 2. 启动与广播模式

App 启动后，如果已有绑定设备：

1. 初始化蓝牙适配器。
2. 以 `needLocation: true`、`accessBackgroundLocation: false` 初始化 `kux-bluetooth`，并启动绑定设备广播扫描。
3. 从 `realtime_broadcast_data` 最近一条记录恢复 `eventSeq`，避免首次广播误判为新事件。
4. 启动基准时间心跳（`device-tick.ts` 的 `tick.start()`），首次 tick 立刻判定，此后每 60 秒一次；并按 30 分钟节奏投递事件兜底读取。
5. `App.uvue` 启动 Android 保活服务（`startKeepAliveService()`）；保活只维护扫描和上传兜底，不发 GATT 命令。

首次创建 `vital_sync_state`（包括老版本升级）时，`B` 初始化到当时的 `stableCeiling`，不把“过去没有基准记录”解释成“过去 30 天全部待补”。若 `B` 已经位于当前 30 天保留起点或更早，启动时也清空旧 ready 并恢复到 `stableCeiling`，优先避免故障版本继续追逐凭空产生的 30 天积压；这版暂不区分“故障版本污染”和“确实超过 30 天没启动 App”，长时间未使用后的历史恢复留待后续处理。晚于保留起点的已有 `B` 在普通冷启动时原样续用，所以 30 天内关闭 App 形成的真实缺口仍会补。绑定另一台设备时同样清空旧 ready 区间并从新绑定时刻初始化，不能继承上一台设备的进度。

插件初始化配置本身不开启 `accessBackgroundLocation`。Android 10+ 的“始终允许”定位权限在首次绑定成功后才用业务弹窗引导用户去设置页开启，避免打断首次连接流程。

广播扫描只匹配当前绑定设备 ID。收到绑定设备广播后，按新版 24B `custom_adv_data_t` 解析：

- `utc`
- `voltage`
- `status` 派生出 PPG 佩戴、行为、活动状态
- `hr`
- `ppi`
- `spo2`
- `bhr`
- `status2` 派生出 `eventSeq` 和电池状态
- `steps_everyday`
- `calorie_everyday`
- `rmssd`

日志示例：

```text
[BOOM-ADV] 收到广播 #12: phone=... utc=... diff=1s timeValid=true eventSeq=5 ...
```

## 3. 广播时间校验

每条广播会先做缓存包识别，再校验 `utc` 是否可信。

缓存包识别规则：

- 如果本条广播 `timeValid=false`，并且 `utc` 没有比上一条可信广播前进，同时 `vHex` 和上一条可信广播完全相同，先记为一次疑似缓存。
- 连续 3 次疑似缓存后，才认为是 Android 扫描层缓存旧包。
- 缓存包直接丢弃，不入库、不更新首页、不触发事件、不触发校时。
- 丢弃后重启绑定广播扫描。
- 只有“缓存包”这一种原因的重启扫描有 20 秒冷却，避免同一批旧包触发连环 stop/start；扫描无回调、绑定设备无回调不受该冷却限制，否则第二轮恢复会被冷却吞掉。
- 连续 3 次重启扫描仍未恢复时升级为硬恢复：关闭适配器、重建 `kux` 实例、重新挂载适配器/连接/notify 监听，再打开适配器重新扫描。硬恢复另有 60 秒冷却，冷却期内先做轻量重启。
- 硬恢复后如果仍收不到有效绑定广播，主页写入错误提示“未收到设备广播，请确认设备在附近、电量充足且系统蓝牙权限正常”；重新收到有效绑定广播后自动清除。

扫描无回调保护：

- 绑定广播扫描启动后，如果 12 秒内没有任何 `deviceFound` 回调，认为系统扫描管线卡住。
- 这种情况日志里会看到 `startDiscovery 成功` 和 `discovering=true`，但没有任何 `[BOOM-ADV] 收到广播` 或“未匹配绑定设备”日志。
- App 会主动重启绑定广播扫描。
- 有回调但没有绑定设备时，绑定广播扫描持续 18 秒没有绑定设备回调也会重启扫描（`bound scan stale`）。
- 12 秒监视器在通过检查后会继续挂下一轮，直到扫描停止或 generation 变化。
- 这个保护和缓存包识别不同：缓存包是“有回调但包是旧的”，扫描无回调是“完全没有回调”。

后台保活扫描兜底：

- `kux-bluetooth` 初始化配置为 `needLocation: true`、`accessBackgroundLocation: false`；后台定位由首次绑定后的引导弹窗让用户手动开启。
- Android 保活服务由 `App.uvue` 启动，`service` 原因最短每 60 秒唤醒一次 App 侧任务；上一轮还在执行时会跳过等待，只单独跑一次扫描兜底。
- 如果已有绑定设备、当前没有 GATT 连接（`currentDeviceId == ""`）、没有 GATT 命令通道占用（`isGattTaskBusy() == false`），也不在删除设备，保活会检查绑定广播扫描状态。
- 如果绑定广播扫描未启动，保活会直接拉起绑定设备过滤扫描。
- 如果绑定广播扫描已启动，但超过 70 秒（`BOUND_BROADCAST_MAINTAIN_IDLE_MS`）没有任何扫描回调或绑定广播处理，保活会轻量重启扫描（`hardRecover=false`）。
- 保活 tick 会调 `device.tick.start()` 并补一次 `tick.poke("keepalive")`（后台没有广播帧驱动，靠它兜底叫心跳），同时跑一次 `uploadData()`。
- 保活只维护扫描和上传，不发送 GATT 命令；历史、事件、校时仍统一走 scheduler。
- 保活扫描维护失败只记录日志，不影响 PPI/睡眠上传兜底。
- 代码结构上，广播扫描分为三层：`startBoundBroadcastScan()` 只启动，`restartBoundBroadcastScan()` 只重启，`maintainBoundBroadcastScan()` 只检查并按需调用前两者。

后台兜底日志示例：

```text
[SCAN] 检查绑定广播扫描: reason=keepalive service, bound=..., scanning=true, purpose=boundBroadcast, current=, gattBusy=false, idleMs=..., maxIdleMs=70000
[SCAN] 绑定广播扫描无活跃回调，重启扫描
```

时间校验规则：

- `diff <= 10s`：认为时间可信，允许入库、更新首页、写 PPI。
- `10s < diff < 60s`：丢弃本条，不自动校时。通常是短暂缓存、扫描延迟或系统回调延迟。
- `diff >= 60s`：如果不是缓存包，认为设备时间明显异常，丢弃本条并尝试自动 GATT 校时。

坏时间广播不会写入：

- `realtime_broadcast_data`
- `ppi_data`
- 首页实时 store

自动校时抑制条件（满足任一就不入队）：

- 最近 60 秒内有可信 GATT 时间：`0x34` 读回值与手机相差 ≤10 秒，且最近 60 秒内收到过 notify。
- 最近 60 秒内已经尝试过一次自动校时。

自动校时流程：

1. 广播模块丢弃本条异常数据，并向 `DeviceGattScheduler` 投递 `timeSync` 加急任务。
2. Scheduler 停止广播扫描，连接/重建 GATT。
3. 发送 `0x33` 设置当前手机 UTC 秒。
4. 发送 `0x34` 读回设备时间确认，3 秒内等待设备时间序号前进。
5. 成功后继续顺带执行队列里已有任务，最后断开并恢复广播扫描。

如果校时失败：

- 不清除绑定关系。
- 停止绑定广播扫描，并停止历史自动检查。
- 清空当前实时展示和广播调试信息。
- 断开当前 GATT 连接，不恢复广播扫描。
- 提示用户：设备时间异常且自动校时失败，请检查设备后恢复广播扫描。

## 4. 实时数据入库与首页展示

时间可信的广播会写入 `realtime_broadcast_data`。

首页、metrics、状态页、负荷页优先使用本地最新广播数据展示：

- 心率：`hr`
- 静息心率：`bhr`
- 血氧：`spo2`
- 心率变异性：`rmssd`
- 步数：`steps_everyday`
- 卡路里：`calorie_everyday / 100`

其中 `rmssd` 是 HRV 实时值，`ppi` 不再作为 HRV 展示值。

单个字段的展示有效范围：`hr` / `bhr` 在 28~240 之间，`spo2`（放大 10 倍的整数）在 700~1000 之间，`rmssd` 大于 0，`steps_everyday` / `calorie_everyday` 大于 0。超出范围只保留上一条有效展示值，不影响该秒原始值照常入库。

实时展示过期规则：

- App 启动或页面进入时，会从 `realtime_broadcast_data` 恢复最近一条广播记录。
- 如果最近一条广播记录的 `received_at` 距离当前超过 5 分钟，实时展示清空。
- 正常收到可信广播后，会刷新 `received_at` 并重新启动 5 分钟过期计时。
- 单个字段无效时不立刻清空该字段，例如 `hr=0`、`bhr=0`、`rmssd=-1`，会保留上一条有效值。
- 如果整个广播 5 分钟没有更新，首页、metrics、状态页、负荷页的实时值显示为 `-` 或空值。

## 5. PPI 保存与批量上传

时间可信的广播每秒都写入 `ppi_data`，包括 `hr / spo2 / ppi` 全为 `0` 的原始值；不能按生理范围过滤后丢弃该秒：

- `timestamp = 广播 utc`
- `hr = 无效时 0`
- `spo2 = 无效时 0`
- `ppi = 无效时 0`

历史生命体征 `0x3A/0x3B` 没有血氧字段，按原始每秒记录判定：

- 只有完整六字节都是 `FF`（`FFFFFFFFFFFF`）才是无效秒；全零和部分字段为 `FF` 都是有效秒，进入本地上传队列。
- `timestamp = response.startSec + secondIndex`，跳过无效记录时保留原始秒索引，不压缩时间。
- `hr / ppi` 保留解析值，包括 `0`；`spo2 = 0`。不再按心率或 PPI 是否大于零过滤。
- 排除尚未产生的未来秒；重读相同秒按本地时间戳主键去重。历史重放可修正旧版保存的 `hr=255, ppi=65535` 占位记录并重新排队，但不会无依据删除旧记录。

上传策略：

三个触发点，一个入口 `uploadData()`（在 `upload.ts`，`BluetoothUploader`）：

| 触发点 | 位置 | 职责 |
| --- | --- | --- |
| 心跳（主） | `device-tick.ts` 的 `runTick()` 每轮调一次 | 上传本轮所有待传记录 |
| 历史补录落库后 | `readVitalRange` 的 finally → `scheduleUpload` | 异步排空，不阻塞 GATT 释放 |
| 保活 tick | `keepalive.ts` 的 `runKeepAliveTickAsync` | 后台消费积压 + 失败重试 |

- **主触发是心跳，不是广播，也不再有「整分钟」。** 秒级广播落库后只喊一声 `tick.poke("broadcast")`，由心跳按 60 秒限流统一决定判不判、传不传。广播侧不认识「分钟」「判定」「上传」任何一个概念——早先的 `uploadCompletedMinuteIfCrossed` / `onMinuteCompleted` 连同 `lastBroadcastMinuteSec`、`minuteUploadBusy` 一起删除。
- 「整分钟」本来是纯粹的历史包袱：判定早已不按分钟切（第 8 节），`B` 和已记账区间都是秒级的，而上传取的是「所有 `timestamp <= 冻结上界` 的待传记录」，根本不关心分钟。
- **上传入口只有 `uploadData()` 一个。** 三个触发点都调它，内部只有 PPI 与睡眠两个私有助手；PPI 那侧只做「有待传记录 + 不在失败退避中就传」，**没有条数与间隔阈值**——节奏由触发点决定，不在这里再节流一次。（早先的「攒够 30 条 或 距上次 30 秒」既让秒级实时流成了真正的驱动源，又把整分钟触发挡在门外：分钟边界那一刻两条判据都为真，整分钟等于没触发。已删除。）
- **上传节奏因此是「约 60 秒一批」，而不是「一整分钟一批」。** 心跳可能落在分钟中间，同一条实时流的秒会分两次上传（例如 12:00:35 传 35 秒，12:01:35 传剩下 25 秒）。服务端按 `time` 逐秒接收，这不影响正确性。
- **判定与上传是两件事。** 合格判定（第 8 节）依据的是本地 `ppi_data` 有没有那一秒，不是上传结果；上传失败时 `uploaded` 保持 0，由重试路径继续消费，不会因为弱网把已经收齐的秒判成待补。
- **上传节奏完全由触发点决定，编排层自己不带定时器。** 心跳每轮都调 `uploadData()`，已经覆盖了「消费积压 + 失败重试」的全部事情；`upload.ts` 里曾有一套没人调用的 60 秒定时兜底（`startUploadTimer` / `UPLOAD_RETRY_INTERVAL_MS`），它被删掉了——留着等于留了第二个节奏来源，一旦被接回去，上传节奏又有两个互不知情的驱动。心跳若真停摆，该修的是心跳。
- 保留 `PPI_UPLOAD_MAX_BATCHES = 10` 作为积压排空的上限；正常实时路径每轮心跳只有一批。**单批的条数上限不在编排层**，而是 `data-manager.ts` 的 `PPI_UPLOAD_PAGE_SIZE = 300`（SQL `LIMIT`）——分页是查询的属性，编排层再放一个同名常量会让人以为改它能改批大小。
- 每批按采样时间从旧到新最多取 300 条，只查询本批待传记录，不一次加载全部积压数据。
- 每轮开始时先冻结窗口上界：`SELECT MAX(timestamp) FROM ppi_data`，即本轮开始前已经落库的最新秒。本轮只上传不晚于该上界的记录，上传期间实时广播新落库的秒留给下一轮。
- 这条上界是必需的：实时广播每秒落库一条，比一次 HTTP 往返还快（一轮往返约 1~2 秒），如果每批都重查“当前所有未上传”，循环会被新到的秒一直喂饱，唯一的出口“没有待传记录”永远不成立，只能连发到批次上限。冻结上界后，实时场景一轮就是 1 批。
- 一轮最多连续处理 10 批，这个上限是给历史补拉积压用的（一轮最多消化 3000 条）；还有积压时释放上传锁，由下一轮心跳继续消费。
- 查询待传数据前就持有上传锁，避免心跳、保活 tick 和历史补拉并发取出同一批记录。
- 单批失败立即结束本轮，失败批和后续数据保持 `uploaded=0`；失败后退避 `UPLOAD_FAILURE_BACKOFF_MS = 60 秒`，这期间的触发点（心跳也好、保活 tick 也好）都会跳过 PPI 上传，即使积压已超过 300 条也不密集重试。退避只作用于这条自动路径，测试页手动上传直接调 `uploadPpiData()`，不受影响。
- 已明确上传成功的批次单独标记，不受后续批次失败影响。
- 自动补录（`readVitalGapGroup`）成功落库后，通过 `scheduleUpload()` 异步触发上传，不等待网络请求完成，避免弱网和多批积压延长 GATT 占用。重复的待执行上传调度合并，上传仍走同一套锁、批量与重试规则。测试页的快速读取和手动 `0x3A` 连续读取（`readVitalDataAuto`）不走 `scheduleUpload()`，它们落库的秒由下一轮心跳消费。
- 每批上传成功并标记 `uploaded=1` 后，立刻调用 `pruneUploadedPpiBefore(手机当前秒 - 30 天)` 清理已上传且超出本地 30 天审计窗口的 PPI。清理 SQL 固定为已上传条件，未上传行永不因保留期被删除，也不会因此被重新补读；清理失败会走 PPI 上传失败路径并让本轮返回失败，但本批已标记的行保持已上传。
- 除上传成功后的清理外，没有额外的每日兜底清理任务。

上传确认与返回值：

- PPI 和睡眠上传开启严格成功校验：HTTP 200 还必须返回数值 `code=0`（若同时带 `status`，须为 `success`），或无 `code` 且 `status="success"`。
- HTTP 200 的空响应、普通字符串、未知结构和明确失败响应不能作为上传成功依据，记录保留为待上传。其他业务接口维持原有响应兼容策略。
- 服务端确认成功后，只标记本批记录；本地标记写入失败也返回失败，保留记录以便重试。
- 数据库查询失败与“没有待传记录”区分处理，查询失败不返回上传成功。
- `uploadPpiIfPending()` 返回 `true` 表示没有待传 PPI，或本轮 PPI 已全部传完；失败退避中、通道忙、仍有积压或失败返回 `false`。
- 成功/失败只按本轮冻结窗口内的记录判定：窗口外新到的实时秒留给下一轮，不让实时流把上报结果一直压成“失败”。
- `uploadData()` 分别尝试 PPI 和睡眠上传，只有两者都成功或没有待传记录才返回 `true`；不再固定返回成功。
- 自动历史读取返回的 `uploadScheduled=true` 仅表示已调度上传，`uploadAttempted=false` / `uploadOk=false` 表示读取结果不包含实际上传确认；最终结果查看 `[BOOM-UPLOAD]` 日志。手动生命体征读取仍可等待上传并返回实际结果。
- 登录凭证与刷新凭证均过期时，请求明确失败并退出登录；刷新失败时拒绝所有等待请求、清空刷新队列并复位刷新状态，避免请求悬挂导致上传锁无法释放。

诊断日志记录批次、条数和采样时间范围，例如：

```text
[BOOM-UPLOAD] 上传PPI数据: batch=1, count=300, from=..., to=...
[BOOM-UPLOAD] PPI上传成功: count=300
[BOOM-UPLOAD] 本轮批次结束: remaining=...
PPI上传失败，保留未上传数据
上传响应未明确确认成功
```

这里的成功仍以现有服务端响应为依据，不代表已逐条核对云端落库；旧版本已经标记 `uploaded=1` 的数据不会自动重传。

日志中如果看到 `batch=1`，说明本轮只有一批；连续出现多批（`batch=2` 及以上）是积压排空的正常表现。反之，如果连续多批的 `count` 都只有 1~2，且 `from`/`to` 恰好等于打日志时的当前时间，说明窗口上界没有生效——传的不是积压而是上传过程中实时进来的秒，需要检查 `MAX(timestamp)` 冻结逻辑。

## 6. 新事件触发与读取

广播 `status2` 的高 4 位是 `eventSeq`。

处理规则：

1. App 启动时从 `realtime_broadcast_data` 最近一条记录恢复 `eventSeq`。
2. 收到广播时，如果 `eventSeq` 相比上次变化，标记 `hasNewEvent=true`。
3. 先按 30 秒静默窗口合并：佩戴、断开、读取事件都可能让 `eventSeq` 短时间连续跳变，静默结束后才真正入队，避免连续连接多次。
4. 向 `DeviceGattScheduler` 投递 `readEvent` 加急任务。
5. 如果队列里已有事件读取任务，会替换成最新一次；如果事件读取正在执行，则跳过重复入队。

事件兜底读取：

- 自动同步循环每 30 分钟投递一次普通优先级 `readEvent`。
- 兜底读取不依赖广播 `eventSeq` 变化。
- 兜底只负责“读事件”；读到 `SleepResult` 后才会保存睡眠并上传。
- 如果队列里已有 `readEvent`，或正在执行 `readEvent`，兜底不会重复入队。

事件读取流程：

1. Scheduler 停止广播扫描，连接/重建 GATT。
2. 发送 `0x3C`，按时间窗口读取最近 24 小时事件头。
3. 根据设备响应自动发送 `0x3D` 续读。
4. 解析事件明细并保存睡眠相关数据。
5. 打印解析摘要。
6. 读取结束即结束本次事件任务，不再顺带补最近窗口；连接期缺秒由第 7 节描述的下一轮自动检查补回。
7. 如果队列里还有历史补缺任务，继续执行；所有任务结束后断开回广播。

事件读取期间由 scheduler 持有临时 GATT 连接。页面不再维护 `testMode`；当前状态应由 `currentDeviceId`、`isGattTaskBusy()` 和 `getOnlineInfo()` 推导。

事件读取不需要额外的额度控制：它天然有界——最多 20 页（`EVENT_SYNC_MAX_PAGES`），每页之间 250ms，每段响应最多等 10 秒，而任一批次超时会直接结束本次读取（不会累积多次超时）。实测上界约 37 秒，低于整轮 120 秒预算。手动测试页同样只由用户停止或设备结束决定。

日志中正常事件读取会出现：

```text
[BOOM-EVENT] 开始读取新事件: device=..., eventSeq=..., window=...~..., maxCount=...
[BOOM] 事件头(0x3C): type=..., snRange=...~..., timeRange=... ... ~ ... ...
[BOOM] 事件追加: count=10, total=...
[BOOM] 睡眠事件处理完成: found=..., saved=..., skipped=...
[BOOM-EVENT] 新事件读取完成: status=..., pages=..., items=..., savedSleep=..., saveOk=..., 上传已尝试=..., upload=...
[BOOM-UPLOAD] 上传睡眠数据: count=..., ids=..., [time=..., 睡眠窗口=...~...(up=...,sleep=...), detail长度=..., 深=..., 浅=..., 其他=..., 无分期=..., detail头=...]
[BOOM-UPLOAD] 睡眠数据上传成功: count=...
[BOOM-EVENT] 新事件解析结果:
```

### 睡眠从事件到云端：四行日志定位断点

“查询数据提示没有睡眠数据”要区分是**没读到**、**没上传**，还是**上传了但没有有效分期**。这四行各自回答一个否则无法从日志回答的问题：

- `睡眠事件处理完成: found/saved/skipped`：事件里到底有没有 `SleepResult`。`found>0, saved=0` 说明事件解析出来了但被 `toSleepData` 判为无效（`ts<=0`、`sleepOnsetTime<=awakeTime`、`awakeTime<0`），此时另有一条 `睡眠事件跳过` 带原始 hex；`found=0` 说明这段窗口设备没回睡眠事件。
- `新事件读取完成: ... 上传已尝试=...`：`savedSleep>0` 但 `上传已尝试=0` 说明根本没走到上传（读取被停止，或 `persistSleepData=false`）；`上传已尝试=1, upload=0` 才说明上传真的失败了。
- `上传睡眠数据: ... detail长度=..., 无分期=...`：**判定“服务端说没有睡眠数据”的关键**。`detail` 是逐秒睡眠分期串，`深/浅/其他` 是有效分期计数，`无分期` 是落成 `"0"` 的秒数。`无分期` 等于 `detail长度` 说明这段窗口本地没有任何活动数据，服务端据此判定“没有睡眠数据”。
- `睡眠数据上传成功/失败: count=..., ids=...`：失败必须带 `ids`，因为下一轮能否补上取决于这条记录是否还留在 `uploaded=0` 集合里。

#### `saved` 涨了但库里没有：`INSERT OR IGNORE` 会吞掉约束冲突

出现过一次「日志里 `found=1, saved=1`，但睡眠库为空、`最近睡眠` 是暂无查询结果、**全程没有一条 SQL 报错**」。这是两个问题叠加：

1. 旧库的 `sleep_data` 还带着老 DDL 的 `record_count INTEGER NOT NULL`。老迁移走的是 `ALTER TABLE ... DROP COLUMN`，而这条语法要 SQLite 3.35+（Android 14 才带），`minSdkVersion` 21 的机器上直接语法报错，列留在原地。
2. `storeSleepData` 用的 `INSERT OR IGNORE` 把 NOT NULL 冲突当成“可忽略”：行被跳过，SQL 算执行成功。于是只看 `execute()` 的返回值会把“一行都没写”当成成功。

修法是两条一起：迁移改成整表重建（只用 CREATE / INSERT SELECT / DROP / RENAME，不依赖高版本语法，历史行与 `uploaded` 状态按列名交集搬运），`storeSleepData` 改为返回是否真的写进去、写失败打 `睡眠数据写入失败`，读取端按这个返回值计数。**判断这类问题就看 `睡眠数据写入失败` 有没有出现**——它出现说明写库这一步就断了，跟事件、上传都无关。

`上传睡眠数据` 这行刻意不打印完整 `detail`：一夜的 `detail` 有两万多字符，整体序列化会一次写满诊断缓冲区。只记长度、分期计数和前 24 位，既能判断分期是否有效，又不挤掉别的日志。

`detail` 全为 `"0"` 是独立成因，与上传无关：逐秒分期来自 `sleep_status_data`，这张表只在广播每秒写入（`storeBroadcastSleepActivity`），上传时按事件窗口读取并组装。所以组装出来全 0 只有一种可能——**该窗口内的广播分期没有落库**。窗口换算本身是可靠的（`startSec = reportTimestamp - bedtime`、`endSec = reportTimestamp - wakeTime`，两侧同为设备秒），组装循环也已被测试覆盖到 23400 秒满窗口无缺。

分期缺失有两个已知成因：

1. **广播在窗口内没有覆盖。** GATT 读取期间广播扫描是停的，连接期留下的缺秒由历史读取补齐，但历史读取只补 `ppi_data`，不补 `sleep_status_data`。所以如果一夜里设备长时间没有广播（关机、离得远、App 被杀），这段窗口就没有分期。
2. **广播入库失败。** `storeBroadcastRecordByDevice` 原先把 `storeBroadcastPpiData` 放在 `if (record != null)` 里面——`record` 是 `realtime_broadcast_data`（首页展示表）的写入结果。这张表写失败时，PPI 与睡眠分期会被一起跳过，症状正是整晚 `detail` 全 0。现在两个落库调用都在该判断之外，各自的成败互不牵连。

要区分这两种成因，看同一时段的 `[BOOM-ADV] 收到广播 #N`：窗口内有连续广播却仍全 0，就是成因 2（或当时的入库失败）；窗口内没有广播，就是成因 1。

协议上 `VitalData_Per_Second` 的 `status` Bit[2:0]（`状态说明.txt` 2.1.3）与广播 activity 编码一致，用历史读取补分期在协议层可行，但**当前设计不走这条路**：分期由广播暂存、事件只提供起止时间，不从历史读取反推分期。

### 睡眠上传有独立的锁

睡眠上传不共用 PPI 的上传锁。两者写不同接口、不同表，互不冲突，而 `uploadPpiData` 一轮最多连发 10 次请求；共用一个锁时，这期间到达的睡眠上传会整段被丢掉——只留一条 info 日志，记录停在 `uploaded=0`，用户侧表现为“有睡眠事件但没有上传”。跳过时现在会写明原因（`原因=上一轮睡眠上传未结束` / `原因=设备未连接`），带上 `count` 与 `ids`。


## 7. 连接生命周期

GATT 会话期间必须停止广播扫描，这段时间的秒级数据不会通过 0x50 进来。**每一次连接都必然制造缺秒。**

**这一节没有特殊机制：连接就做连接自己的事（校时 / 事件 / 补录），做完断开。它期间掐掉广播留下的缺秒，按普通缺口处理——下一次连接来补。**

连接不再设时长上限：一次 flush 需要读多久就读多久，补到完成再断开。原来「120 秒必须断开把通道还给广播」的约束取消了。

### 7.1 连接期间形成的缺口

连接掐掉一段广播，这段秒既不在 `B` 里、也不在 `vital_ready_ranges` 里，所以**它天然就是 `listRepairGaps()` 会返回的普通缺口**（7.2）。断开恢复广播后：

1. 广播正常续上，新的秒照常落库、分类、推进 `B`。
2. 连接期那段缺秒留在缺口列表里。
3. **下一次连接**（10 分钟自动检查，或任何本来就要连的任务）把它一起读掉。

不需要 force-B、不需要读自己的空洞、不需要空洞识别、不需要接续判定。

### 7.2 连接空洞本来就是普通缺口

不存在「识别这段缺秒是连接造成的空洞还是丢包造成的缺口」这个问题：两者在 `listRepairGaps()` 眼里**完全一样**，都是「既不在 `B` 里也不在 `ready_ranges` 里的秒」。

**这条认识删掉了整套「空洞识别」机制。** 早先设计的 `holeFrom`（停广播那一刻的整秒）、`tail`（连接留下的空洞宽度）、`BROADCAST_RESUME_GRACE_SEC`（宽限值）、`CONNECTION_LONG_THRESHOLD_MS`（连接时长判据）、广播接续判定、以及断开前的定向补读，都是为「识别并特殊处理连接空洞」造的东西，**全部删除**。

### 7.3 稳定状态：每次连接补上一次的，留下一次补

**每次连接都会留下一点缺口，由下一次连接补掉——这是被接受的设计，不是需要消除的问题。**

设连接的**固定开销**为 `O`（停扫描 / 直连 / 握手 / 断开静默 350ms+120ms / 重启扫描，与被读的数据量无关），本次要补的缺口为 `G`，GATT 读取速度 82.8 倍实时（1 页 2 分钟数据 = 1.45 秒）：

```
本次连接留下的空洞 = O + G/82.8，留给下一次连接
```

迭代式收敛到 `O/(1-1/82.8) ≈ 1.012·O`，所以空洞**有界、不会滚大**，稳态就是「每 10 分钟连一次，每次补掉上一次留下的几秒，再留下几秒」。代价是永远有几秒到十几秒的缺口在等下一次自动检查——而那几秒的真数据**设备里一直有**（那个时段用户在戴着设备，秒数据在 flash 里），等 10 分钟不会丢。

**一个可选优化，不做也不影响正确性**：如果 `O` 恰好落在 8 秒以内，下一次连接的空洞会被容差直接吸收（连续缺失 < 9 秒）、连缺口都不产生，于是稳态更进一步变成「没有缺口」。这是顺带的好处，不需要为它调任何东西。

### 7.4 `MINUTE_SETTLE_SEC` 与这件事无关

两个常量经常被混在一起，但它们毫不相关：

| 常量 | 作用 |
| --- | --- |
| `MINUTE_SETTLE_SEC = 10` 秒 | 等多久才**判定**（避开在途的广播包 / 未落的 Flash）。只决定「什么时候判」，不决定「判合格还是不合格」 |
| `MINUTE_MAX_MISSING_RUN_SEC = 9` 秒 | 连续缺失达到多少就**判不合格**。它才是「几秒的空洞可以被容差吸收」的来源 |

所以调 `MINUTE_SETTLE_SEC` 只会让 `B` 落后更多或更少，对连接留下的空洞**没有任何影响**。

连接留下的最后 10 秒（`stableCeiling` 之后）不属于任何缺口——它们尚未稳定、本轮不记账，由广播在走完余量时正常吸收。连接结束时 `B` 与当前时间的差距就是这样来的，不是缺口的累积。

**广播在线时**：`B` 由分类推进到 `stableCeiling ≈ now - 10s`，每次分类都在追。
**广播离线时**（App 后台/关闭）：`ppi_data` 不增长，缺口会累积，但此时没有广播要保护，连接可以一直补到 `stableCeiling`，补完断开放广播。

### 7.5 连接最小间隔

`CONNECT_INTERVAL_MS = 10 * 60 * 1000`（在 `device-tick.ts` 里）。心跳的 `maybeConnect()` 按这个间隔检查缺口；一轮连接把积压补完，下一次连接至少 10 分钟后。这也顺带提供了缺口读取失败的天然退避（缺口不落库，没有 `retry_at`）。

**加急任务不受这个间隔限制**：校时、广播事件变化触发的事件读取、用户手动的设置类命令（0x31/0x35 等）都立即连接——这些本来就是「必须连」的事。**缺口不在这里**：没有加急缺口，缺口只等这个 10 分钟的间隔。


## 8. 持久历史补录：基准时间与缺口推导

后台不保持 GATT 长连接；心跳（`device-tick.ts`）每 10 分钟检查一次缺口，有缺口才投递 scheduler，由 scheduler 临时连接执行；事件兜底仍为每 30 分钟。心跳没有「启动延迟」——第一次 tick 就把 App 关闭期间积压的时间判完，延迟只会让首次补录更晚。单轮异常记进 `lastError` 并记日志，下一轮继续。

### 8.1 基准时间 `B`

整个补录模型只有一个游标 `baseline_sec`（下称 `B`），它满足：

> **`[0, B)` 的每一秒都已经记账完毕**，不需要再补。

「记账完毕」有两种形式：

1. **合格（qualified）**：该段的数据完整度达标（见 8.2）。
2. **已确认（confirmed）**：设备已被读取过该时间段，并返回了完整声明范围的响应，确认没有更多数据（未佩戴 / 关机 / 该段设备确实没记）。

**`B` 停驻是预期行为。** 一段不合格时 `B` 卡在该段起点不动，直到这段被补上或被设备确认无数据，才继续前进。`B` 只前进，不后退。停驻时后面合格的秒照样被判定并记入 `vital_ready_ranges`，堆在那里等 `B`（8.3），所以停驻不会导致重复判定。

### 8.2 合格判定

**判定不看分钟边界。** 判定单元是**整个未记账区间**——`[B, stableCeiling)` 减掉 `vital_ready_ranges` 之后剩下的那几段。判的只有两件事，两件都与分钟无关：

| 条件 | 判据 | 常量 |
| --- | --- | --- |
| 没有连续缺 9 秒 | 每一段连续缺失都 `< 9` 秒 | `MINUTE_MAX_MISSING_RUN_SEC = 9` |
| 缺失总量不到 30% | `missing * 100 < 区段长度 * 30` | `MISSING_TOTAL_PERCENT = 30` |

第 `s` 秒可以判定，当且仅当 `s + MINUTE_SETTLE_SEC <= now`（8.6 的 `stableCeiling`）。

**为什么不去按分钟切。** 按分钟切会**在分钟边界上把一段连续缺失拆成两半**，两半各自都可能小于 9 秒，于是一段真实的 9 秒空洞被容差误吃。整分钟这个单位本身也不承载任何语义——设备记的、广播发的、`0x3A` 收的都是裸的 UTC 秒，一分钟只是人读日志时的习惯刻度。

**两条判据管的是两件事，必须分两遍算。**

1. **连续缺失**（逐段）：一段连续缺失达到 9 秒就是**真缺口**。空口空洞是连续的，所以这一条是真正起作用的约束，它把容差的实际覆盖范围压在 8 秒以内。真缺口把这一段切成若干**候选区**，缺口本身不属于任何候选区。
2. **缺失总量**（逐候选区）：它防的是「很多段各 8 秒、加起来占了一大半」这种稀疏情形——只看连续缺失是看不出来的。不过关则整个候选区都不记账。

第 1 遍先切、第 2 遍再算总量，是因为总量是「这一片有多稀疏」的度量，**必须在一个不被真缺口打断的连续区域里算**。整段一刀切会让一处真缺口把它后面几十秒在场的数据一起作废——`B` 停在缺口前面，后面合格的秒照常记进 `vital_ready_ranges` 等它，所以那些秒没有理由跟着陪葬。

**第三关只作用于贴着右端的缺失段**：右端之外还没判到，它可能还更长，不能按当前长度放过。右端之外已确认时（这一段的右端是被已记账区间截断的，不是 `stableCeiling`），贴着右端的段才是完整的。不设这一关，一个横跨 `stableCeiling` 的 11 秒空洞会被拆成两段各 8 秒以内，被容差整段吃掉。

**这两条阈值是「要不要去设备读这一段」的触发器，不是最终裁决。** 判不合格 → 成为缺口 → 连设备读一次。设备的回答才是终局：

- 设备有这段数据 → 秒数据落进 `ppi_data`，该段合格，并入 `vital_ready_ranges`。
- 设备没有这段数据（该段全 `FF`）→ 该段**确认无数据**，同样并入 `vital_ready_ranges`。

所以**任何一次读取都会让缺口消解**，`B` 一定能继续前进。如果只有「取到数据」才算消解，设备确实没记录的那一段会永远不合格、`B` 永远卡死——这是必须避免的死循环。

### 8.3 缺口：由 `B` 与已记账区间相减得出

**缺口不存表。** 它由 `B` 和 `vital_ready_ranges` 直接相减得出：

```
缺口1 = [B,                ready[0].fromSec)
缺口2 = [ready[0].toSec,   ready[1].fromSec)
...
缺口N = [ready[N-1].toSec, 读取右端)
```

`vital_ready_ranges` 为空时，缺口就是 `[B, 读取右端)`。因为 `B` 只能推进到 `ready[0].toSec`，所以**任何时刻只有一个活跃缺口**：

> **缺口 ≡ `[B, ready[0].fromSec)`**

补完这个缺口、推进 `B`、消费掉 `ready[0]` 之后，原来的 `ready[1]` 变成新的 `ready[0]`，下一个缺口**自动**就是 `[B, ready[0].fromSec)`。不需要枚举、不需要排序、不需要存储、也没有 `retry_at` / `attempts` 这类持久退避字段。

**读取右端 = `stableCeiling(now)`。** `listRepairGaps()` 只返回 `stableCeiling` 之前的缺口；之后的秒故意不读——那时读得到但记不了账（8.5），读了也白读，还会让「补到没有缺口为止」这个终止条件永不成立。

**缺口与 ready 区间都是秒级的，不对齐整分钟**，端点直接当 `startSec` 用（设备接受任意时间戳，见 8.4）。因此一条 ready 区间可能是半分钟的（例如 `[12:00:20, 12:00:28)`），缺口也可能只有几秒——减法在秒上是自洽的。

**相邻 ready 区间要合并。** 秒级右端下，两次广播跨分钟判定可能产出 `[12:00:00, 12:00:28)` 与 `[12:00:28, 12:01:00)` 这样首尾相接的两条；写入走整表归一化（先 `DELETE` 再 `INSERT OR IGNORE`）天然完成合并，避免行数虚增。行数受「不合格段数」约束而不是时间长度，所以整体重写的成本可以忽略。

**几秒宽的小缺口不值得单独触发一次读取。** 它们由 8.4 的桥接合并进邻近的读取窗口；若整个缺口组都只有几秒宽，则由容差直接吸收（连续缺失 < 9 秒），连缺口都不产生。

### 8.4 读取：缺口内从后往前，桥接碎缺口

补录的基本循环：

```
读缺口 [B, ready[0].fromSec)  →  落库 / 确认  →  B 推进，消费 ready[0]  →  下一个缺口
```

两方面不是一回事，不要混：

- **缺口顺序**：从 `B` 往前走——先补第一个缺口。
- **缺口内读取方向**：`anchor` 取缺口的**末端**，`direction = 0` 向更早翻页，翻到缺口起点。

纯「一次只补一个缺口」在丢包场景下会碎片化。例如 `12:05` 和 `12:07` 两段不合格、`12:06` 合格，则 `ready[0] = [12:06, 12:07)`，会拆成两个缺口、两条 `0x3A` 链路。丢包率高时一小时能拆出几十条链路。所以实际读窗口 **= 第一个缺口向前桥接跨过的短 ready 区间**：

```
读窗口 = [B, 末端)
末端 = 从 ready[0].fromSec 起，只要「下一个缺口的宽度」+「中间 ready 区间宽度」都在 bridgeSec（120 秒）内就继续向前合并
```

桥接跨过的秒本地已有，不重复入库，只计入 `bridgeSeconds` 供日志和弹窗展示。这等价于「相距 120 秒内的缺口合成一组」，但表述仍从 `B` 出发，仍然只有一个活跃缺口组，不破坏 8.3 的模型。

**`anchor` 取缺口末端的原始秒，不做任何对齐。** 设备的 `0x3A` 收的就是裸的 UTC 秒，任意时间戳都行，设备没有「必须整分钟」的要求。对齐是我们自己发明的约定，代价是丢掉最多 59 秒的可读窗口——对连接留下的几十秒缺口尤其明显（对齐后窗口可能直接变空）。现有代码的历史游标本来就是设备返回的 `page.startSec`（任意秒），从来没有对齐过。`minutes = 2` 是**每页步长**（翻页时向更早走 2 分钟），不是「窗口必须对齐到 2 分钟」——两者不是一回事。

一次连接把 `listRepairGaps()` 的缺口全部处理完（带桥接）。

### 8.5 记账规则与每页落库

「把一段范围记为已记账」只有一个入口 `markReady(from, to, nowSec)`：

```
记账 [from, to)：
  to = min(to, stableCeiling(now))
  有效秒        → 数据
  FF / 缺行     → 设备确认「这里没有」
  超出 to 的部分 → 不记账，留在缺口里等它自然稳定（不重读、不确认）
```

`stableCeiling` 之前的范围已经稳定，`FF` 是确定的「设备没有」，可以永久记账。超出它的部分尚无定论，所以既不写 `vital_ready_ranges`、也不当作可读缺口，只是等时间走过去。`to` 是秒级的，不向上取整到分钟。

**`advanceBaseline()` 因此不需要任何 clamp**：`vital_ready_ranges` 里的每一段右端都不超过 `stableCeiling`，`B` 的上界自动成立。约束在数据写入那一刻就成立，而不是事后去拦 `B`。

每收到一页（`saveVitalPage`），做两件事，顺序固定：

1. **有效秒写入 `ppi_data`**（`uploaded=0`），先把数据留住。无效秒（完整六字节全 `FF`）不写 `ppi_data`，但它们同样是「设备确认这里没有」——所以整页范围仍然记账。这正是「任何一次读取都会让缺口消解」的落点。重读相同秒按本地时间戳主键去重；历史重放可修正旧版保存的 `hr=255, ppi=65535` 占位记录并重新排队，但不会无依据删除旧记录。
2. **把该页可确认的范围并入 `vital_ready_ranges`**，右端由 `markReady` 封顶在 `stableCeiling`，调用方不需要自己算。

落库与记账任一步失败就抛错、不推进，已提交的页面保留。

### 8.6 一个余量、一个边界

```
stableCeiling(nowSec) = nowSec - MINUTE_SETTLE_SEC   -- 记账右端，也是缺口右端、分类右端
```

`MINUTE_SETTLE_SEC = 10` 秒。以 `now = 12:30:05` 为例：`stableCeiling = 12:29:55`。

**这是唯一的边界，三处共用**：记账右端（允不允许写进 `vital_ready_ranges`）、缺口右端（`listRepairGaps()` 的右端）、分类右端。除此之外没有第二个边界；读取窗口直接取缺口端点和「设备返回的最晚秒」。整分钟对齐唯一保留的地方是 30 天保留窗口的起点。

它的含义是「最后一秒已经等够余量、可以放心记账」，所以是「`now` 往前 10 秒」，与分钟边界无关。

**两条写入路径共用同一个余量**，它们的余量本质是同一件事——都是「10 秒量级的传输/写入延迟」：广播分类时最后几秒的广播包还在途中；页面记账时最后几秒设备可能还没写好。若真机测出固件写入延迟确实大于 10 秒，**只需调大这一个值**，三处一起调整，不会出现两处漂移。它同时是运行时可调的。

### 8.7 推进 `B`

纯表操作，**不查 `ppi_data`**：

```
保留窗口钳制：B 早于 30 天保留起点 → B 直接跳到保留起点，并删掉早于它的 ready 区间
循环：
  B 落在 ready[0] 内（fromSec <= B < toSec）→ B 前进到 ready[0].toSec，消费 ready[0]
  否则               → 停
```

**保留窗口那一步必须直接跳到保留起点，不能逐秒放行**：`B` 可能因设备长期连不上而停在几个月前，逐秒是几千万次带表查询的循环。同时也**必须在分类之前跑**：全新安装时 `B = 1`，不先钳制，分类就要从 1970 年判到今天，既无意义也会把内存撑爆。这是唯一保留整分钟对齐的地方。

调用时机：

1. **心跳**（唯一入口）。`device-tick.ts` 的 `runTick()` 顺序做三件事：`classify()` → `advanceBaseline()` → `uploadData()`。分类推进到 `stableCeiling(now)`，把本轮新稳定的秒并进 ready 区间，再推进 `B`。
2. **连接结束**：不需要特殊动作。连接期间停广播产生的缺秒按普通缺口处理，下一次连接补（第 7 节）。
3. **连接的检查**另按 10 分钟节流（`maybeConnect()`）。心跳每 60 秒跑一次，但只有距上次检查超过 10 分钟时才看一眼缺口。

心跳的驱动来自两条路：前台是广播每落库一帧 `tick.poke("broadcast")`，后台是保活 tick 和 60 秒 `setInterval` 兜底。限流在 `poke()` 内部——调用方只管说「有新数据了」，不需要自己判断该不该跑。

这三步就是过去 `sync.planHistorySync()` 的全部内容；分类是幂等的纯本地计算，所以每轮都从 `B` 走一遍没有副作用，`B` 因此永远贴着 `stableCeiling`，不需要「已分类游标」这种额外状态。

**一轮 tick 里 `B` 只读一次。** 分类只写 `vital_ready_ranges` 不改 `B`，所以 `runTick()` 开头读到的那个值对紧随其后的推进与列缺口都成立，它作为参数一路传下去（`clampToRetention(nowSec, knownBaseline)`），不再各自重读。这既是省一次跨桥查询，也少一个断网时的异常点——`getBaseline()` 读失败会抛。`advanceBaseline()` 里的消费循环同理：`listReadyRanges()` 一次读出、就地消费，不每轮迭代重查全表。效果是积压时（几十条相邻 ready 区间等着被消费）一轮 tick 的查询从 51 次降到 7 次。

### 8.8 App 没开 / 长时间没有广播

因为缺口是推导出来的，而分类永不停止，这个场景不需要任何特殊处理：

1. 重开后 `B` 停在关闭前的时刻，它到现在的全部时间都是「未记账」。
2. `classify()` 立刻把它们判完。App 关闭期间没有广播 → `ppi_data` 为空 → 整段是不合格 → 整段是缺口。
3. `listRepairGaps()` 直接给出这段缺口，从缺口**末端起读**，不必等分类追平。
4. 读取后 `B` 推进。

**设备一跳就能确认掉「确实没数据」的整段。** 如果设备在这期间没被佩戴，查 `anchor=now` 向更早翻时首页的 `startSec` 会直接落在缺口起点之前——一次 `0x3A` 就把整段确认成已记账，不会翻几千页。只有设备**真有数据**时才逐页读，而那正是我们要读的。所以「App 关 3 天」的代价：没佩戴 → 一次往返；佩戴了 → 读 3 天的数据（本来就要读）。

**没有单轮扫描上限。** 老流程的 6 小时 `HISTORY_RECONCILE_SCAN_SEC` 是为了限制「遍历 30 天 86 万个时间戳」，而现在查询只覆盖未记账区间，App 关闭期间 `ppi_data` 为空（查询瞬间返回零行），区间算术在内存里做。所以 3 天的空白是一次零行查询 + 若干次区间算术，没有理由截断。

### 8.9 两分钟倒序读取

这里的「两分钟」是**读取单位**，不是窗口大小。协议允许 `minutes ∈ {2, 5}`，生产路径固定用 2：一个窗口靠 `0x3A → 0x3B → 0x3B → …` 逐页读完，每页 2 分钟。

窗口是任意连续区间 `[fromSec, toSec)`，一般远大于 2 分钟：一个 90 分钟的缺口是 45 页。首个命令使用 `0x3A(..., direction=0, minutes=2)`，之后同一查询会话用 `0x3B(minutes=2)` 往前读。

设备实际返回可能少于两分钟，也可能因长期关机直接跳到很早的时间；不机械地将游标减去 120 秒。短页只要包含完整的 6 字节秒记录就接受，包含全 `FF` 的秒记录仍表示无效秒；只有半个秒记录才视为响应截断。协议规定短页未返回的后部时间无有效数据，因此有效秒按实际内容落库，但记账覆盖该页声明的完整 `n × 60` 秒范围。每页提交后，游标推进到该页实际 `startSec`，并裁剪到目标下界。续页必须向更早时间推进，防止固件反复返回同一页而空转。

首个 `0x3A` 回包若 `response.startSec > 查询锚点`，表示设备历史索引发生跳转，常见于设备校时后。该页不入库、不推进当前游标，但保留设备已经建立的历史续读上下文，继续发送 `0x3B` 向更早页面翻；直到页实际落入目标范围才保存。

短页、全 `FF` 页、以及逐秒有效记录数为 `0` 都不是停止条件。测试页显示的「设备返回短页」只是展示信息，不代表数据错误或读取已结束。

响应必须包含完整分钟摘要，秒数据可为零到 `n × 60` 条完整六字节秒记录。存在残缺字节或超过分钟声明的秒数视为截断响应：记录错误日志、停止本轮，不保存页面数据，也不推进游标。

### 8.10 一次补不完、断线或获取失败

- **一次连接不设时长上限**，需要补的缺口就一直补，补到完成再断开。缺口全部读完时，`B` 推进到 `stableCeiling`，下一轮 `listRepairGaps()` 返回空。连接自己留下的缺秒不特殊处理，它是普通缺口，由下一次连接顺带补掉（7.1）。
- **收尾判定**：
  - 设备返回段早于整个缺口（`page.startSec < 缺口.fromSec`，或 `startSec = 0`）→ 该缺口设备无数据，整段按 8.5 记账。这是设备关机 / 未佩戴的正常路径，**不是失败**，继续读下一组。
  - 响应结构截断（秒数超出声明、残缺 6 字节记录）→ 视为链路错误，中止本轮。
  - 超时 / 发送失败 → 中止本轮。已提交的页面保留，剩余缺口留在原地，下一次连接重来。
- 补录落库后调用 `scheduleUpload()` 异步消费，不阻塞 GATT 释放。
- **失败退避由连接间隔天然提供。** 缺口不落库，所以没有 `retry_at` / `attempts`。读取失败后缺口仍在，下一次连接至少 10 分钟后才来，自然重试。
- 补录完成后不需要额外的「核验」任务：`B` 自己会重新推进，合格的秒自动被吸收进基准时间。
- 每一条 `0x3A` 或 `0x3B` 发出后最多等待 8 秒。若设备没有 notify 回包，结果记为 `TIMEOUT (wait vital response timeout)`；不把刚发出的这一页或其时间范围记为已补录。
- 本轮规划或数据库异常不会退出自动同步循环；仍保留后续重试机会。

一轮补录在连接开始时冻结 `planNow`、`stableCeiling` 与缺口列表，成功只针对这份计划判断；连接耗时带来的保留窗口移动和尾部新秒记为 `deferredTail`，不能算成本组推进，也不能反过来把本轮变成永远追不完的移动目标。

结果判定只有一套：

| 结果 | 当前页记账 | 本组结果 | 后续 |
| --- | --- | --- | --- |
| 合法完整页 / 合法短页 / 全 FF / 零秒页 | 按协议明确覆盖范围记账 | `DONE` | 继续或完成 |
| `startSec=0` / 已跳到目标窗口以前 | 剩余目标范围确认无数据 | `DONE` | 完成本组 |
| 超时 / 发送失败 | 当前失败页不记账 | `TIMEOUT` / `SEND_FAILED` | 保留剩余缺口，下一次 10 分钟检查重试 |
| 截断 / 页面不后退 / 数据或 ready 写入失败 | 当前失败页不记账 | `STOPPED`，且写入失败时 `saveOk=false` | 保留剩余缺口，下一次重试 |
| GATT busy / 解绑 / 主动停止 | 不新增记账 | `STOPPED` | 不在同一 flush 自旋，等待下次触发 |
| 达到显式页数限制（仅手动/调试入口可能设置） | 已提交页保留 | `LIMIT` | 自动补录不把它算成功；剩余范围下次重试 |

已成功提交的旧页面不回滚；下一轮由 `B + vital_ready_ranges` 重新推导，只读取剩余范围。本组成功必须同时满足 `status=DONE && saveOk=true && B>=本组右端`；即使读取器返回 `DONE`，只要整个窗口尚未记账，仍记为失败并停止同一连接里的后续组。也不能因为 `B` 随 30 天保留窗口自然移动就声称补录成功。

### 8.11 哪些时间可以算已经检查

- 只确认设备实际返回的页面范围，并裁剪到缺口范围及 `stableCeiling`。
- 稳定边界就是 8.6 的 `stableCeiling`（当前时刻减 10 秒），**不再有第二个页面记账专用余量**。更新的秒先等它稳定，下一轮再判。
- 时间有效、分钟数合法且分钟摘要完整的零秒列表页（`vitalData.length == 0`），按声明的 `n` 分钟记账；全 `FF` 页只说明对应页面没有有效秒，同样并入 `vital_ready_ranges`。
- 终止标记、超时和发送失败都不能用作区间覆盖证明。
- 已记账区间表示设备读取完成或本地数据达标，不表示云端上传完成。待上传由 `ppi_data.uploaded` 单独记录。
- 已记账区间也不制造 `ppi_data` 行，更不等于本地 PPI 完整。它只表示「此绑定下这一秒已有归属」，因此只用来避免重复补读。
- 早于本地 30 天保留窗口的时间不参与分类、不展示为待补、不创建 GATT 任务，也不会被保留期清理逻辑重新拉起。

### 8.12 哪些情况触发加急连接

后台默认每 10 分钟检查一次（心跳里的 `maybeConnect()`）。触发加急连接（绕过 10 分钟间隔）的只有本来就「必须连」的事：

| 触发 | 判据 |
| --- | --- |
| 校时 | 广播时间异常 |
| 事件读取 | 广播 `eventSeq` 变化 |
| 手动命令 | 测试页 / 设置类命令（0x31/0x35 等） |

**缺口不制造连接。** 加急缺口连接已删除：加急的收益是「早几分钟补上几秒丢包」，成本是「多一次连接 + 掐掉一段时间广播」，而用户看不到任何差别（实时展示走广播流）。缺口只搭心跳那 10 分钟检查的顺风车，`CONNECT_INTERVAL_MS` 也是「缺口要等多久才被补」的上界——包括连接自己留下的缺口。「广播静默后恢复」这个触发同样删除：那种积压是普通缺口，等下一次自动检查即可。

```text
[BOOM-PARSER] 生命体征响应秒数据截断
```

这几行是排查补录问题的支点，各自回答一个否则无法从日志回答的问题：

- `刻度` / `分类完成`：`B` 和分类右端在哪、这一轮把多少秒从「未记账」变成了「已记账」或「缺口」。`未记账 = 新记账 + 新缺口`，不等就说明还有秒被阻塞。
- `基准停驻`：`B` 卡在哪、卡了多久。`阻塞起点` 就是唯一的活跃缺口起点。
- `段不合格`：这一段为什么不合格——总缺失、最长连续缺失、阻塞段各是多少。贴着 `stableCeiling` 的失败不打这行（只是还没等到数据，下一轮会重判），打出来会把日志冲满。
- 一轮最多展开 5 条 `段不合格`，其余由 `不合格段日志已省略` 汇总，避免历史积压时重复日志淹没真正的 GATT 超时。
- `缺口组结束` 的 `本组推进` / `complete`：这一组的读取有没有真的转成记账，用 `B` 的前后差量及是否越过本组右端度量。`B` 没动或没越过右端就说明读取没有完整转成记账（被 `stableCeiling` 封顶、设备跳页、或落库失败），而这在 `status=DONE` / `落库` 两列上完全看不出来。**这是「读了但 `B` 不动」的第一现场。**
- `缺口组读取结束` 的 `有效秒` / `全FF秒`：`全FF秒` 与页数一致说明设备确实没记这段；`有效秒` 远小于页数说明解码有问题。
- `页落库`：每页落了多少秒、记了哪一段账。`新增秒` 远小于页长是正常的（设备全 `FF` 或重读）。
- `补录结束`：规划的缺口秒数和实际落库秒数的差额，以及 `失败组`。`计划剩余缺口 > 0` 表示本轮冻结计划没读完，下一轮继续；`deferredTail` 只表示连接期间走过的新时间，不属于本轮成败。

所有补录、页面落库、基准推进和响应解析错误都通过 `.cool/service/logger.ts` 进入诊断日志；不要只 `throw` 或仅输出 `console`。这样测试页的诊断记录和导出日志能保留异常上下文。

历史补录排在 scheduler 队尾，避免旧数据积压挡住校时、设置和事件读取。
## 9. GATT 任务队列与通道锁

自动 GATT 业务统一进入 `DeviceGattScheduler`：

- `timeSync`：加急，广播时间异常时立即执行。
- `readEvent`：广播 `eventSeq` 变化时加急执行；30 分钟兜底时普通优先级执行。
- `historyRepair`：尾部任务，心跳每 10 分钟检查一次缺口，有缺口才入队。
- `manualCommand`：测试页和手动 GATT 命令。

任务身份：

- 每个任务都有 `seq`，用于日志追踪一次入队到执行的生命周期。
- 每个任务都有 `key`，用于合并同类任务。
- `timeSync` 的 key 是 `timeSync`，重复入队时保留最新校时参数。
- `readEvent` 的 key 是 `readEvent`，广播新事件和 30 分钟兜底共享同一个槽位。
- `historyRepair` 的 key 是 `historyRepair`，重复入队只保留一个补缺任务。
- `manualCommand` 的 key 带 `seq`，所以不会合并。

去重规则：

- 队列里只保留一个 `readEvent`；新事件加急任务会替换已排队事件任务。
- `readEvent` 正在执行时，新的事件任务和事件兜底任务都会跳过，不再排下一轮重复读取。
- 队列里只保留一个 `historyRepair`；补历史正在执行时，新的补历史任务会跳过。
- `manualCommand` 不去重，用户触发几次就执行几次。
- flush 过程中如果又收到新的 flush 请求，会记录最强触发原因；只有队列里确实还有任务时才继续下一轮。
- 连接失败或 GATT 忙时，不会立刻自旋重试，剩余任务等待下一次触发。**连接不再有 120 秒时长预算**（第 7 节），一轮 flush 会把任务做完再断开。
- 同一轮内已经执行过又回队的任务不会再被取用（`flushDeferredKeys`）：否则它会在同一轮里立刻再跑一次，空转到整轮超时，反而把排在其后的尾部补录饿死。
- 但回队不等于没人管：事件任务排队时，每 30 分钟的事件兜底检查会为它触发一次 flush，不必等到下一次 `eventSeq` 变化；新的 flush 轮次会重置回队名单。

Scheduler 执行顺序：

1. 加急控制类：`timeSync`、`manualCommand`
2. 数据类：`readEvent`
3. 尾部任务：`historyRepair`

Scheduler 执行流程：

1. 队列为空时不连接。
2. 有加急任务时立即 flush；普通历史/事件兜底由定时检查 flush。
3. flush 开始时停止广播扫描，连接或重建 GATT。
4. 每轮开始重新校验 service / notify，避免复用假连接。
5. 按顺序执行任务，所有任务共用 GATT 锁。
6. 任务完成后断开并恢复广播扫描；校时失败时断开但不恢复广播扫描。

所有会占用 GATT 命令通道的任务都要先抢锁（`GattTaskName`）：

- `timeSync`：自动校时
- `event`：事件读取及事件兜底
- `vitalGap`：缺口补录（自动和测试页手动共用）
- `vitalAuto`：测试页手动生命体征连续读取
- `unbind`：删除设备时远端解绑

`vitalRecent`、`manual`、`unknown` 类型已在 `GattTaskName` 中声明，但目前没有读取器占用它们。抢锁失败会输出 `[BOOM-GATT] 通道忙: current=..., request=...`。

日志示例：

```text
[BOOM-SCHED] 任务入队: seq=12, key=readEvent, kind=readEvent, priority=urgent, size=1
[BOOM-SCHED] 任务合并: seq=12, key=readEvent, kind=readEvent, priority=urgent, size=1
[BOOM-SCHED] 执行任务: seq=12, key=readEvent, kind=readEvent
```

如果频繁看到“通道忙”，说明自动任务之间仍有冲突，需要调整触发时机。

## 10. 模式切换

### 广播模式

- 停止当前 GATT 任务后的连接占用。
- 断开当前 GATT。
- 启动绑定设备广播扫描。
- 页面用 `getOnlineInfo()` 显示广播在线/离线。

### 临时 GATT 任务

- 停止绑定广播扫描。
- 优先直连缓存绑定设备。
- 连接成功后只初始化协议通道，不自动读固件、不自动校时、不自动读 0x50。
- 执行队列任务，完成后断开并恢复广播扫描。

测试页不再手动切换连接模式；点击 GATT 命令后进入队列执行。

## 11. 删除设备与解绑

删除设备时：

1. 通过连接层进入 GATT 连接模式。
2. 发送 `0x41`，`code=1` 请求设备解绑并清除数据。
3. 等待 `0x41` 响应，`result=0` 表示成功。
4. 无论设备是否确认，最终清理本地绑定和本地数据。

注意：自动校时失败不会清绑定，只提示用户。

产品只允许绑定一台设备。连接并绑定另一台设备前，客户端会以一个 SQLite 事务清空旧设备的 PPI、睡眠、广播和持久补录进度；清空失败则不切换本地绑定，避免旧数据按新设备地址上传。

`[BOOM-BASE] 刻度` 就是一轮心跳的起点，正常约每 60 秒一条，`reason` 说明这一轮被谁唤醒（`startup` / `broadcast` / `keepalive` / `timer`），只影响日志不影响行为。

上传正常：

```text
[BOOM-UPLOAD] 上传PPI数据: batch=..., count=..., from=..., to=...

[BOOM-UPLOAD] 本轮批次结束: remaining=...
[BOOM-DATA] 清理已上传 PPI: before=..., count=...
[BOOM-UPLOAD] 上传睡眠数据: count=..., ids=..., [time=..., 睡眠窗口=...~..., detail长度=..., 深=..., 浅=..., 其他=..., 无分期=..., detail头=...]
[BOOM-UPLOAD] 睡眠数据上传成功: count=...
[BOOM-UPLOAD] 无待上传睡眠数据
```

异常重点：

- `SEND_FAILED`：通常是 protocol 未 ready 或连接已断。
- `TIMEOUT (wait vital response timeout)` / `TIMEOUT (wait event batch timeout)`：发送后没有等到 notify 回包，可能连接断开或设备未响应。日志里没有 `hadNotify` 字段，只有上面这两种 message。
- 连续小批量上传（一轮里 `batch` 递增而每批 `count` 只有 1~2、`from`/`to` 等于当前时间）：检查本轮窗口上界是否失效，是否仍按“当前所有未上传”取数。正常形态是**每轮心跳一批**：`[BOOM-BASE] 刻度:` 每 60 秒一条，紧随其后 `上传PPI数据: batch=1, count≈60`。
- 频繁自动校时：检查是否被缓存旧广播误触发。
- 事件读取 `TIMEOUT pages=0`：检查 0x3C 是否有回包，notify 分片是否被重组。
- `上传响应未明确确认成功`：检查接口响应是否符合已有成功约定，不直接把 HTTP 200 当作成功。
- `本地上传标记保存失败`：服务端可能已接收，本地仍会重试，需结合采样时间和设备编号核对。
- `[BOOM-TICK] 本轮心跳异常，下轮继续`：一轮失败被心跳兜住，下一轮（≤60 秒）继续，不能当作永久停止。测试页的 `deviceStore.tick.lastError` 会保留最后一次错误。
- `基准停驻` 连续多轮 `阻塞起点` 不变：`B` 卡在同一处，缺口一直没被补掉。看同一行的 `缺口秒` 是否在涨——涨说明是广播离线期的正常积压，等广播恢复会一次性处理；不涨而 `B` 又不动，检查读取是不是一直失败（看 `[BOOM-HISTORY] 补录结束` 的 `失败组` 与 `ok`）。
- `缺口组结束` 里 `本组推进=0`：这一组读到了东西但没转成记账。先看同一组的 `status` 与 `落库`：`落库 > 0` 而 `B` 不动，说明秒都落在 `stableCeiling` 之后（记账被封顶）；`落库 = 0` 说明设备返回的全是 `FF` 或读取失败。
- `段不合格` 里 `阻塞段数 >= 1`：这一区间有连续缺失 ≥ 9 秒的真缺口。若 `缺失` 远大于 `阻塞秒`，说明这一区间里还有多段较短的缺失被总量那一关挡下（稀疏），不是单个空洞。
- `分类完成` 里 `未记账 != 新记账 + 新缺口`：区间算术和合格判定不一致，属于实现问题而不是数据问题。
- `设备返回段早于目标窗口，按无数据收尾`：设备最新数据早于整个目标窗口（长期关机是正常原因），该组按无数据记账结束，不是失败；同一次连接里后面的缺口仍会读。如果这条日志频繁出现但你确信设备刚有数据，检查设备是否已完成校时。
- `初始化基准时间表失败`：`vital_sync_state` / `vital_ready_ranges` 不可用，本轮不会规划任何 GATT 任务，需要先排查数据库打开失败。
- `睡眠上传跳过: 原因=...`：睡眠上传被跳过。`原因=上一轮睡眠上传未结束` 说明另一轮睡眠上传还在飞（只影响睡眠自己的锁，与 PPI 无关）；`原因=设备未连接` 说明 `deviceAddress` 为空。两种都不是失败，下一轮会重试，记录仍在 `uploaded=0`。
- `上传睡眠数据` 里 `无分期` 等于 `detail长度`：这段窗口本地没有任何睡眠分期，服务端会判定“没有睡眠数据”。成因与上传无关，见 §6 的说明。
- `睡眠数据上传失败: count=..., ids=...`：服务端可能已接收，本地仍会重试；用 `ids` 对照 `sleep_data.uploaded` 可以确认下一次是否补上。
- 诊断日志文件（`Download/BOOM/logs/<yyyyMMdd>/diagnostic-<HHMMSS>-<N>.txt`）：日志按批自动落盘，**不受内存/SQLite 1000 条上限约束**。排查长时段问题时按日期目录取对应批次的文件。文件名里只有时刻和序号——日期已由目录表达，`-N` 是同一秒内的序号。

测试页现在只有六个独立的全屏弹窗入口：快速历史读取、历史缺口补录、生命体征协议、事件协议、设备控制、数据诊断。页面自身不再维护 `testMode`、连接模式开关或缺口操作，只负责打开弹窗和把命令投递到 scheduler。页面正文还有一个「基准时间与缺口」面板，直接展示 `B`、`stableCeiling`、`vital_ready_ranges` 条数、待补总计和每条缺口的起止与桥接跨度；它挂在心跳（`deviceStore.tick`）的规划/执行 revision 上，只有真的发生过规划或补录才重读，不轮询数据库。

“数据诊断”弹窗的“总览”显示 history session 摘要：基准时间 `B`、已记账区间数、当前缺口数与缺口秒数。它只查询数据库并展示，不嵌套补录操作。协议日志与诊断日志只读展示，不提供复制/导出——完整日志由自动落盘承担，弹窗里的按钮只能覆盖眼前这一段，反而会让人以为这就是全部。诊断日志面板只渲染最近 200 条，避免长列表卡顿。

“历史缺口补录”弹窗按缺口逐张展示，每张卡片包含：连续读取窗口（含桥接合并后的跨度）、实际待补秒数、窗口内非待补秒数（桥接跨过、连续读取时跳过写入）、预计耗时，以及“补此缺口”。缺口是从 `B` 与 `vital_ready_ranges` 相减推导出来的，没有可寻址的表行，所以卡片上没有游标、重试次数和“已尝试”这类字段——失败退避由 10 分钟连接间隔天然提供。点击“补此缺口”会把这一段的 `fromSec`/`toSec` 交给手动 GATT 任务，执行同一条 `0x3A → 0x3B` 连续链路，按实际回包逐页入库并记账。手动补录不经过心跳，补完会自己抬一次 revision 让弹窗重读，不会留着补录前的旧缺口。

测试页不再有「补录参数」入口（原来的 `HistoryTunePopup` 已删除）。运行时可调值（`minuteSettleSec` 与 `bridgeSec`）的机制仍在 `.cool/bluetooth/history/tunables.ts` 里，默认值即代码常量，本地覆盖走 `storage` 持久化、`setHistoryTunable()` 写入后立即生效（缓存即刻失效，不需要重启）——但**现在没有界面入口，覆盖只能从代码里写**。

测试页的“快速历史读取”提供近一天、近三天和近一周入口。它是一次独立测试读取：不设总页数上限（`maxPages: 0`，由目标时间或用户停止决定），不推进基准时间，也不写 `vital_ready_ranges`。读取过程显示目标范围、已读页数和已解析秒数；“停止当前读取”同时作用于快速读取与手动 `0x3A` 连续读取，停止后仍保留已解析页面供导出。结束、到达设备历史末端、超时或发送失败后，页面同样保留本次已经解析的全部响应页。点击“保存到下载”后，CSV 直接写入手机公共目录 `Download/BOOM/`，可在系统文件管理器的“下载”中查找，页面也会显示相对路径；CSV 每个已解析秒一行，包含协议时间、本地时间、页起点、页/秒序号、HR、PPI、状态、步频、加速度和有效标记；全零秒保持有效，完整 FF 秒以 `valid=0` 保留，导出仅用于真机协议核对。


“数据诊断”弹窗和“诊断日志”页面都不再提供复制/导出。完整日志由自动落盘承担：内存与 SQLite 都只保留最近 1000 条，而落盘不受这个上限约束，排查长时间段的问题应当直接取文件。落盘路径是 `Download/BOOM/logs/<yyyyMMdd>/diagnostic-<HHMMSS>-<N>.txt`，按天分目录——一天能写十几个文件，平铺在一个目录下很快就翻不动了。CSV 导出仍平铺在 `Download/BOOM/`，那是用户主动导出的一次性文件，不按天分。

文件名与 MIME 必须一致：MediaStore 会用 MIME 反查扩展名，MIME 是 `text/csv` 而名字是 `.txt` 时，会在文件名后**再追加** `.csv`，导出的日志就变成 `.txt.csv`。`boom-csv-saver` 按扩展名给出 MIME，写日志走 `saveLogToDownloads`，CSV 走 `saveCsvToDownloads`。

自动落盘有两条触发线，满足任一条就写一个文件：攒够 500 条，或距上次落盘超过 5 分钟且已攒够 30 条。只按数量触发的话，空闲期那点零散日志会一直留在内存里，进程被杀就没了；下限则避免空闲时写出只有几行的碎文件。时间条件在每条日志上顺带检查，不用另起定时器——缓冲区里有内容说明日志正在流动，下一条日志自然会来做这次检查。“诊断日志”页面的“立即落盘”把不足一批的余量也写出去；`clear()` 会先落盘再清空，否则用户以为清掉的是屏幕上这些，实际连同没看过的日志一起没了。`clear()` 还必须等初始化读完库再重置内存：`initDatabase` 结束时会把读到的历史日志回填进 `logs`，早于它清空就会被这次回填覆盖，刚启动就点清空会看起来没生效。

App 切到后台时（`App.uvue` 的 `onHide`）会调 `flushArchiveNow()`：进程随时可能被系统回收，缓冲区里的日志还没进过磁盘，丢了就再也拿不回来。落盘失败只丢那一批缓冲，不影响内存和数据库里的日志。

## 13. 云端缺口的排查边界与回归验证

历史自动补录依据基准时间 `B`、本地 PPI 覆盖和设备响应推进，不查询云端缺口：

| 缺失时段的本地状态                          | 排查方向                                                                           |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| 早于最近 30 天                              | 超出本地保留窗口，`B` 直接跳到保留起点，不再扫描、不补录；这不是故障                |
| 本地没有记录，且设备已确认过                | 该段已在 `vital_ready_ranges` 里（合格或设备确认无数据），不会重复补读             |
| 本地没有记录，设备也未曾确认                | 广播接收、时间过滤、分类判定、缺口推导、历史补拉及落库                             |
| 本地有记录且 `uploaded=0`                   | 上传触发、网络、凭证、服务端响应与重试                                             |
| 本地有记录且 `uploaded=1`，云端没有         | 上传确认、服务端落库、设备归属、时间转换；本地补缺不会自动恢复这类旧数据           |
| `B` 卡住不动，缺口也不涨                   | 读取一直失败（看 `补录结束` 的 `失败组`），或读取转不成记账（看 `缺口组结束` 的 `本组推进`） |

历史数据没有血氧字段，仍保存 `spo2=0`，不要求回补广播遗漏的血氧。

客户端回归测试：在项目根目录使用 Node.js 22.18 或更高版本执行 `npm run test:boom`（当前 129 个用例）。测试运行实际 TypeScript 业务逻辑与内存 SQLite，模拟蓝牙/网络边界，覆盖区间工具（合并/相减/计数）、合格判定的两关与分遍（连续缺失切分、总量按候选区算、贴着右端未判完）、真缺口不作废其后的在场秒、`stableCeiling` 封顶、分类幂等、基准推进与缺口停驻、保留窗口跳转、缺口推导与桥接合并、运行时可调参数的默认值/覆盖/失效/重置、零值/全 FF 判定、两分钟倒序读取、设备返回段早于目标窗口按无数据收尾、单缺口无数据不中止本轮后续缺口、冷启动后的断点恢复、截断响应拒绝、区间合并、页面事务回滚与并发隔离、GATT 回队不空转、30 天保留期清理、分批上传与冻结窗口、上传期间实时广播不撑长批次、上传入口唯一且无条数/间隔阈值、上传定时兜底已删除、数据库层只保留有调用方的方法、一轮 tick 只读一次基准且不重扫 ready 区间、小批量立即上传、失败退避、PPI 上传在飞时睡眠上传不被丢弃、睡眠上传的跳过原因与分期统计日志、睡眠事件帧经 0x3C/0x3D 读取后落进 `sleep_data`、写入失败不被计成已保存、旧结构 `sleep_data` 重建后可写入、重组噪声不会冲掉诊断缓冲区、日志按批落盘与空闲期落盘、诊断弹窗只读不导出、广播落库失败不牵连睡眠分期、凭证异常和弹窗组件挂载。

测试替身里事件类型常量、命令码与协议解析函数都取真实实现（`boom-constants.ts` / `boom-parser.ts`）：把它们桩成空对象会让 `LOG_EVENT_TYPE.SleepResult` 变成 `undefined`、事件批次永远解析为空，睡眠链路在测试里被静默跳过，看起来"通过"而实际没测到。项目内的相对 TS 依赖由测试加载器按相对路径自动解析，**不维护别名白名单**——漏一个条目只会在某次改动后才炸，且炸成「Unmocked native import」这种指错方向的报错；桩只用于真正的原生边界（App/BLE/网络/日志）。

发布前仍需通过 HBuilderX 原生编译，并在真机验证断网恢复、后台回前台、GATT 中断后补拉；自动化测试不验证系统后台调度或真实固件行为。
